# Hermes relay S1 — foundation implementation plan (child-per-employee, raw-frame stdio transport)

Contract: `orchestration/tickets/hermes-relay-s1-foundation/contract.md` (revised: child-per-employee). This plan is bound by that contract and adds nothing it does not ask for. Grounding: `orchestration/hermes-relay-redesign/plan.md`, `s0-spike.md`, and the decisions `D-child-per-employee` + `D-relay-raw-frame-transport` in `decisions.md`.

The upstream is a POOL of per-employee stdio children. The relay is a TRANSPARENT relay: it spawns each child on the existing `planner.minds.gateway` **spawn seam** (`SpawnFn` / `ChildProcess` / `spawn_popen`, running `hermes_python -m tui_gateway.entry`) and reads/writes **raw newline-delimited JSON frames on the child's stdio itself** through a new `RawFrameChildTransport`. It does NOT use `GatewayChild`'s typed client methods (`begin_request`/`request`/`wait`/`claim_session_event_ingress`/`next_process_event`) for relaying — those rebuild request frames under their own ids, unwrap responses (dropping the frame), and consume `gateway.ready` (`gateway.py:139-155,270-277,335-358`), so they cannot carry frames verbatim (proven in the Codex review, findings 1-4; ruled in `D-relay-raw-frame-transport`). `GatewayChild` remains untouched, serving the legacy role children. There is no `hermes serve`, no upstream WebSocket, and no reconnect logic anywhere in this design.

This is the **round-3 revision**: the architecture — raw-frame stdio transport on the `SpawnFn`/`ChildProcess` seam, child-per-employee pool, relay-owned id space, 9-method session-lifecycle denylist — is SETTLED and confirmed sound; it is unchanged. This revision applies the targeted hardening ruled in `decisions.md` entry `D-s1-concurrency-scope`: it FIXES a small set of confirmed plan bugs (the keyword-only shutdown call, in-progress-init teardown, a death-vs-registration window, fan-out of all unmatched responses, a mechanically-derived registry test, and the test-file count), BUILDS exactly one deep-edge mitigation (a dedicated bounded init/shutdown executor owned by the pool), and DOCUMENTS two acknowledged residual edges as explicit S1 out-of-scope limitations with rationale (see "## S1 limitations"). Round-2 findings are cross-referenced as `(R-N)`; round-3 fixes as `(R3-x)`.

## 0. Concurrency model (read this first — everything else follows from it)

Two worlds meet in the relay and this plan pins the exact bridge between them. The whole design turns on ONE ordered ingress per child AND ONE ordered egress per child.

- **Thread world (upstream, one dedicated reader + one dedicated writer per child).** Each `RawFrameChildTransport` owns exactly ONE daemon **stdout reader thread** and exactly ONE daemon **stdout-side writer thread** (the outbound drain), plus ONE daemon **stderr reader thread**.
  - The **stdout reader thread** loops on `child.read_stdout()` (a blocking newline read), parses each non-blank line as one JSON object, and hands that **parsed frame verbatim** — IN STDOUT ORDER, through a single **permanent** ordered callback — to the relay, via `loop.call_soon_threadsafe(relay.deliver_child_frame, generation, frame)`. `child.read_stdout()` blocks until a line or EOF; it never returns on a timeout, so there is no "timeout-is-not-death" hazard (R-was-12): the only two outcomes are "a line" or `None` (EOF ⇒ child death).
  - The **outbound writer thread** (R-9, R-3c) drains ONE per-child `queue.Queue[str | _Sentinel]` in FIFO order and performs the blocking raw pipe write `child.send(line)`. Because ALL sends for a child pass through this single thread in enqueue order, the child sees frames in **exact enqueue order**, and no two sends can interleave a half-written line. The writer thread is the SOLE writer of the child's stdin AND the SOLE closer of it on the graceful path (R3-G): `transport.shutdown` enqueues a shutdown sentinel and the writer thread, after draining, calls `child.close_stdin()` itself, so `close_stdin` never races a `child.send` in-flight on another thread. `child.send` writes+flushes on one stdin stream (gateway.py:70-72) and `close_stdin` closes that SAME stream (gateway.py:82-86); routing both through the one writer thread makes them strictly sequential.
  - The **stderr reader thread** appends to a bounded `deque(maxlen=STDERR_TAIL_LINES)` for a diagnostic tail (mirrors `GatewayChild._stderr_loop`); stderr is never routed downstream.

  Because there is exactly one stdout reader and one **permanent** ordered delivery callback per child, responses, session events, and process-level frames (including `gateway.ready`) arrive downstream in **exact child emission order** — the transparent-stream guarantee the contract requires (R-3, R-4 resolved by construction: `gateway.ready` is just another frame on this one path; nothing is demuxed into separate queues; the callback is never swapped — R-1).

- **Async world (downstream).** The relay's downstream WebSocket route runs as a coroutine on the FastAPI event loop, exactly like `tail_events` in `core/ws.py`. It `await`s `websocket.receive_text()` and a writer task `await`s `websocket.send_text()`.

**The bridge — one delivery callback per frame, loop-affine.** `deliver_child_frame(generation, frame)` is a plain (non-coroutine) function that runs **on the event loop** (scheduled by the reader thread via `call_soon_threadsafe`). It does the whole routing/correlation decision synchronously and enqueues the frame onto each recipient downstream's own `asyncio.Queue` via `put_nowait` — no `await` inside it, so there is no `run_coroutine_threadsafe` future to manage and nothing blocks the loop. Actual `websocket.send_text` happens later in each downstream's own writer coroutine draining its queue (see §5), so a slow/broken downstream never blocks the reader thread or any other downstream.

- **Correlation lives in the relay, on one ordered path.** Because the transport delivers the *raw* response frame (carrying its own `id`) on the SAME ordered ingress as events, the relay does response correlation itself: `deliver_child_frame` inspects the frame; if it is an id-bearing response mapped to a `PendingForward`, the relay rewrites the top-level `id` back to the downstream's original id and enqueues the *whole frame verbatim* (error frames included) to that one origin downstream. If it is a notification/event (no id) OR any **uncorrelated** frame (an id present but with no matching pending — including `id:null` parse-error responses AND pool-issued session responses — R3-D/R-7), it is treated as an employee-scoped frame and fanned out to that child's subscribers in ingress order and tee'd. There is no `GatewayRequestHandle`, no `_pending` waiter, no `handle.wait()` — those are `GatewayChild` machinery this transport does not use.

**Rule enforced everywhere — no blocking pipe I/O on the event loop (R-3):**
- The stdout/stderr reads block on their own reader threads (never the loop).
- The downstream→child **raw send** is enqueued (non-blocking `put_nowait`) onto the transport's per-child outbound queue on the loop; the transport's single **outbound writer thread** performs the blocking pipe write off-loop (R-9, R-3c). The loop NEVER performs a pipe write and NEVER blocks on one. (This replaces the prior `run_in_executor(None, transport.send_frame)` per-send model — a single per-child writer thread both serializes sends AND preserves allocation order, so the child wire order claim `[1,2,3]` holds, and the pipe write is off-loop by construction.)
- **Child spawn + readiness wait + the pool's `session.create`/`session.resume`** all run **off-loop**, but NOT on the default asyncio executor. The pool owns a **dedicated bounded initialization executor** and a **separate reserved shutdown path** (R3-G, detailed in §1 and §6). Init forwards run via `await loop.run_in_executor(pool.init_executor, pool.child_for_employee, employee_entity_id)`; `child_for_employee` is fully synchronous (spawn, blocking readiness read, blocking session RPC) and is only ever called from that executor's threads. This bound guarantees that a burst of concurrent different-employee spawns cannot occupy every DEFAULT executor worker (which the downstream route and any other `run_in_executor` also share), and — critically — cannot starve pool shutdown (which runs on its own reserved path, never queued behind saturated init work).

**Shutdown coordinates outstanding work (R-3, detailed in §6).**
- The relay/route **tracks every in-flight forward operation** (a set of `_forward` tasks) and **stops admitting new work** before teardown; the route awaits its in-flight `_forward` tasks to settle (or be cancelled) on disconnect.
- The pool **tracks in-progress spawns** (per-employee init slots, each now carrying its partial transport as soon as one exists — R3-B) and refuses new `child_for_employee` once marked closing.
- Cancelling a `run_in_executor` future does NOT stop its thread — so on child death the transport **wakes** the pool's session responder and the readiness waiter immediately (both wait on a shared death event alongside their own completion event), so no executor thread blocks for the full request/ready timeout (R-3b). Likewise, `pool.shutdown` **directly** tears down each in-progress spawn's published partial transport (R3-B), whose `kill()` unblocks that spawn's `wait_ready`/`_transport_request` immediately.
- `pool.shutdown(deadline)` is **blocking** (transport `wait()`+thread joins). The lifespan runs it **OFF the event loop on the pool's reserved shutdown path** via `await loop.run_in_executor(pool.shutdown_executor, functools.partial(pool.shutdown, deadline=deadline))` (R3-A/R3-G) using the same single absolute deadline. `pool.shutdown` is keyword-only (`shutdown(self, *, deadline)`); it MUST be invoked through `functools.partial(pool.shutdown, deadline=deadline)` because `run_in_executor` passes trailing args positionally and a positional call would raise `TypeError` and skip teardown entirely (R3-A). Because every `wait`/`join` inside `pool.shutdown`/`transport.shutdown` is bounded by `remaining()` against that deadline, the executor call itself returns bounded — the loop never hangs even if an init executor thread is still alive when the deadline expires (that thread's blocking call is a child read/wait that `transport.shutdown` unblocks by `kill()`; §6 states the exact bounded sequence). The pool also shuts its OWN executors (init + reserved shutdown path) down within the same deadline (R3-G, §6).

**Child death is observed on the one reader thread (R-4 fixes single-fire; detailed in §6).** When `child.read_stdout()` returns `None` (stdout EOF), the reader thread calls a single, **atomic-once** `transport._mark_dead()` (guarded by a dedicated `threading.Lock` + boolean — an atomic test-and-set, R-4), then, only if THIS caller won the transition, schedules `relay.deliver_child_death(generation)` on the loop and exits. A write failure on the outbound writer thread (`OSError`/`BrokenPipeError`) also routes through the same `_mark_dead()` — so EOF and a failed write can never double-emit a reset even if they run **concurrently** (R-4; the test drives both via a barrier). `generation` is a per-transport **generation token** (an integer minted at spawn), NOT the employee id, so a delayed death from an already-replaced child cannot retire or cancel the replacement.

### `raw_frame_transport.py` — the raw-frame stdio transport (NEW; the core change)

Purpose: own ONE Hermes child directly over its raw stdio, on the injected spawn seam; give the relay a single ordered ingress of parsed frames, a **single-writer ordered off-loop egress**, a bounded readiness wait, a bounded diagnostic stderr tail, and a deadline-bounded shutdown mirroring `GatewayChild`'s discipline. It uses NONE of `GatewayChild`'s typed methods — it is a peer of `GatewayChild` built on the same `SpawnFn`/`ChildProcess` seam.

Module constants (reuse `gateway.py` values; import them, do not redefine): `READY_TIMEOUT_DEFAULT`, `REQUEST_TIMEOUT_DEFAULT`, `SHUTDOWN_GRACE_DEFAULT`, `STDERR_TAIL_LINES`, `JsonDict` from `planner.minds.gateway`.

- No `RawFrame` wrapper type — a frame is just the parsed `JsonDict` (`dict[str, Any]`), forwarded verbatim.

- **`RawFrameChildTransport`**:
  - `__init__(self, *, hermes_python: str, env: Mapping[str, str], on_frame: Callable[[JsonDict], None], on_dead: Callable[[], None], spawn: SpawnFn = spawn_popen, stderr_tail_lines: int = STDERR_TAIL_LINES)`.
    - `on_frame(frame)` and `on_dead()` are the transport's two outputs; the pool wires them to `loop.call_soon_threadsafe(...)` callbacks that reach the relay on the loop. The transport itself knows nothing about asyncio — it just calls these plain callables. `on_frame` is a SINGLE PERMANENT callback for the transport's whole life; it is NEVER swapped (R-1). (This keeps the transport unit-testable with plain synchronous callbacks and no event loop.)
    - Builds `argv = [hermes_python, "-m", "tui_gateway.entry"]` (identical shape to `GatewayChild`); `self._child = spawn(argv, dict(env))`, wrapping `OSError` as a transport error (mirrors `GatewayChild.__init__` gateway.py:230-233).
    - **Does NOT start the reader thread yet** (R-1, two-phase init). It constructs the outbound queue, the death guard (`self._dead_lock` + `self._dead`), the ready gate, the stderr deque, and the **lifecycle guard (`self._lifecycle_lock` + `self._stdout_started = False` + `self._shutdown_begun = False`, R3-round3-2)**, and starts the **stderr reader thread** and the **outbound writer thread** (both daemon), but leaves the stdout reader thread unstarted until `start_reading()` is called. Rationale: the pool must register the generation with the relay BEFORE any stdout frame (including `gateway.ready`, emitted by Hermes at `entry.py:349` *before* it reads stdin) can be delivered — otherwise the callback would run before the relay binding exists and the frame would be dropped (R-1).
  - `start_reading(self) -> None` — starts the stdout reader thread (`relay-transport-stdout`, daemon). Called by the pool AFTER `relay.register_child(...)` so the permanent `on_frame` callback always has a live binding to route into. **Coordinated with `shutdown` by one `self._lifecycle_lock` + `self._stdout_started`/`self._shutdown_begun` booleans (R3-round3-2):** under `_lifecycle_lock`, if `self._shutdown_begun` is set (shutdown started before we ever read), do NOT start the thread and return (the child is being torn down anyway); otherwise start the stdout thread and set `self._stdout_started = True`. Idempotent (assert-once via the flag). This closes the pre-start race where the pool publishes the partial transport into the init slot, `shutdown` snapshots it, and `start_reading` would otherwise start a reader on an already-closing child.
  - `_stdout_loop(self)` — `while True: line = self._child.read_stdout(); if line is None: break; line = line.strip(); if not line: continue; try: frame = json.loads(line) except JSONDecodeError: continue; if not isinstance(frame, dict): continue; if not self._ready_gate.is_set(): detect-and-set-ready-if-this-is-gateway.ready; self._on_frame(frame)`. On loop exit (EOF): `self._mark_dead()`. Note: the `gateway.ready` frame is STILL passed to `self._on_frame` (it is NOT swallowed) — see `wait_ready`. There is no callback swap and no early-frame consumption anywhere in this loop (R-1).
  - `_outbound_loop(self)` (R-9, R-3c, R3-G) — `while True: item = self._outbound.get(); if item is _SHUTDOWN_SENTINEL: self._child.close_stdin(); break; try: self._child.send(item) except OSError: self._mark_dead(); break`. This is the SOLE writer of the child's stdin AND the sole graceful closer of it: on the shutdown sentinel it drains, then closes stdin itself (so `close_stdin` never races an in-flight `send` on another thread — R3-G). FIFO drain ⇒ the child sees frames in enqueue order (the relay enqueues under its lock in id-allocation order, §4, so the wire order is strictly `[1,2,3,...]` — the R-9 claim holds). A write failure marks death once (R-4) and stops the writer; remaining queued frames are dropped (the child is gone).
  - `enqueue_frame(self, frame: JsonDict) -> None` — the non-blocking egress entry point, called ON THE LOOP by the relay. `if self._dead: return` (best-effort fast drop; the writer also guards); `self._outbound.put_nowait(json.dumps(frame) + "\n")`. It rewrites NOTHING — the caller (relay) has already produced the exact frame to write (top-level id rewritten if it is a request; verbatim otherwise). This is the verbatim-write guarantee (R-11 structural): unknown top-level fields, id-less notifications, arbitrary methods all pass through modulo the relay's single top-level `id` rewrite. Enqueue is non-blocking so the loop never blocks on a pipe (R-3).
  - `_stderr_loop(self)` — append rstripped lines to `self._stderr_lines: deque` until EOF (mirrors gateway.py:300-305).
  - `wait_ready(self, timeout: float = READY_TIMEOUT_DEFAULT) -> None` — blocks on `self._ready_gate` (a `threading.Event`) up to `timeout`. The stdout reader sets `self._ready_gate` the FIRST time it sees a frame whose `params.type == "gateway.ready"` (the same detection `GatewayChild` uses, gateway.py:270-277) — AND forwards that frame to `on_frame` anyway (contract: `gateway.ready` reaches the employee's subscribers, R-3). `_mark_dead()` also sets `self._ready_gate` (so a child that dies before ready wakes the waiter — R-3b); `wait_ready` then checks a `self._ready_seen` flag and raises a transport error if the gate opened by death, not by ready (mirrors gateway.py:316-324). Raises on timeout with the stderr tail attached. Called off-loop by the pool inside `child_for_employee`.
  - `_mark_dead(self) -> bool` — the **atomic single-fire** guard (R-4). Under a dedicated `self._dead_lock`: `if self._dead: return False; self._dead = True; won = True`. Then (outside or inside the lock, but exactly once): set `self._ready_gate`, signal the pool responder death event (via a registered death-waiter callback — see below), and call `self._on_dead()`. Returns `won` so ONLY the winner invokes `on_dead`. EOF (reader thread) and a failed write (writer thread) both call it; if they run concurrently only ONE wins the boolean transition and only that one fires `on_dead` (R-4). `self._dead` is a plain `bool` guarded by `self._dead_lock`, NOT a bare `threading.Event` test-then-set (the old `if event.is_set(): return; event.set()` was a race — R-4).
  - **Death-waiter registration for the pool responder (R-3b).** The transport exposes `dead_event` (a `threading.Event` set inside `_mark_dead`). The pool's synchronous session RPC waits on `(responder.done OR transport.dead_event)` so a child death wakes it immediately rather than after the full request timeout. `wait_ready` similarly checks `dead_event` via `_ready_gate` (already set on death).
  - `stderr_tail(self) -> list[str]` — `list(self._stderr_lines)`.
  - `shutdown(self, *, deadline: float) -> None` — mirrors `GatewayChild.shutdown(grace, *, deadline)` (gateway.py:392-407), coordinating with the outbound writer (R-3c, R3-G) and with `start_reading` (R3-round3-2): under `self._lifecycle_lock`, set `self._shutdown_begun = True` and snapshot `stdout_started = self._stdout_started` (so a not-yet-started reader is never started after this, and we only join a thread that actually started). Then `remaining = max(0, deadline - monotonic())`; enqueue `_SHUTDOWN_SENTINEL` so the writer drains and closes stdin ITSELF on the graceful path (never racing an in-flight `send` — R3-G); then `if self._child.wait(remaining()) is None: self._child.kill(); self._child.wait(remaining())` — the `kill()` breaks a writer thread that is still blocked inside a `child.send` on a wedged pipe (documented as an accepted S1 edge: a mid-`send` blocked write is broken by the process kill, not by a cooperative writer interrupt — see "## S1 limitations"). Then join the stderr and outbound writer threads within `remaining()`, and join the stdout thread within `remaining()` **only if `stdout_started`** (joining a never-started `threading.Thread` raises `RuntimeError` — R3-round3-2). A hung child is killed inside this method because `wait(remaining())` returns `None` on timeout, and the reader threads exit on the EOF that follows kill. Idempotent (safe to call on an already-dead transport, and on one whose reader never started).
  - `@property alive(self) -> bool` — `not self._dead` (read under `_dead_lock` or via the `dead_event`).

### `employee_child_pool.py` — the employee child pool

Purpose: owns N `RawFrameChildTransport`s, one per employee entity; spawns on demand with identity env; creates/owns exactly one session per child; respawns dead children on next demand; is the SOLE issuer of `session.create`/`session.resume`; shuts all down within one shared deadline. Owns its OWN bounded initialization executor and a separate reserved shutdown path (R3-G). **Never holds a blocking call under its global lock** (R-2).

Module constants (reuse the `shared_gateway` RPC shapes; do NOT import `shared_gateway`):
- `SESSION_COLS: Final = 100` — matches `shared_gateway.SESSION_COLS`.
- `RELAY_SESSION_SOURCE: Final = "panels-relay"` — the `source` for `session.create`. Distinct from `SESSION_SOURCE`/`CHAT_SOURCE` so relay-owned sessions are self-labeled in the store and can never be confused with role-child sessions (satisfies "creates fresh sessions or resumes only sessions it created"; a source tag is the only in-store ownership marker).
- `CHILD_CLEANUP_BUDGET_SECONDS: Final = SHUTDOWN_GRACE_DEFAULT` — the named operational cleanup budget (R-12) for the bounded teardown of a stale or partially-initialized child during a respawn/failed-spawn (replaces the undefined `SHORT` the prior draft used). It is derived from the imported `SHUTDOWN_GRACE_DEFAULT` (gateway.py:26). Each such teardown computes `deadline = _monotonic() + CHILD_CLEANUP_BUDGET_SECONDS` and calls `transport.shutdown(deadline=...)`. (The pool-wide `shutdown` uses the app's single shared deadline, NOT this constant; this constant governs only the in-line stale/partial cleanup that happens *during* a spawn, where there is no ambient app deadline.)
- `INIT_EXECUTOR_MAX_WORKERS: Final = 8` (R3-G) — the bound on the pool's dedicated initialization `ThreadPoolExecutor`. A named, small bound so a burst of concurrent different-employee spawns is capped and can never occupy every default-executor worker (starving the downstream route or shutdown). The value is deliberately modest for an off-by-default S1 foundation; it is the ONLY tuning knob and is documented here.

**Pool-owned executors (R3-G — addresses default-executor starvation).** The pool constructs and OWNS two off-loop execution resources, so init work and shutdown never contend on the default asyncio executor:
- `self._init_executor: concurrent.futures.ThreadPoolExecutor(max_workers=INIT_EXECUTOR_MAX_WORKERS, thread_name_prefix="relay-pool-init")` — every `child_for_employee` (spawn + `wait_ready` + session RPC) runs here, scheduled by the route/relay via `loop.run_in_executor(pool.init_executor, ...)`. Exposed as a read-only property `init_executor`.
- `self._shutdown_executor: concurrent.futures.ThreadPoolExecutor(max_workers=1, thread_name_prefix="relay-pool-shutdown")` — a SEPARATE reserved single-worker path for `pool.shutdown`, exposed as `shutdown_executor`. Because it is distinct from `_init_executor`, `pool.shutdown` can never be queued behind saturated init work; it starts immediately and applies its internal `remaining()` deadline regardless of how many init threads are busy. (The lifespan schedules `pool.shutdown` via `loop.run_in_executor(pool.shutdown_executor, functools.partial(pool.shutdown, deadline=deadline))` — §7.)
- Both executors are shut down INSIDE `pool.shutdown`, within the same deadline (§6): after all transports are torn down, the pool calls `self._init_executor.shutdown(wait=False, cancel_futures=True)` (any still-running init future's transport was already killed by the in-progress-slot teardown below, so its thread unblocks on EOF). The **LAST action** of `pool.shutdown` is `self._shutdown_executor.shutdown(wait=False, cancel_futures=True)` (R3-round3-4). `wait=False` is safe to call from the shutdown executor's OWN worker (which is where `pool.shutdown` runs): it marks the executor shut down and wakes the single worker, which exits after the current `pool.shutdown` task returns — so the reserved worker is reclaimed rather than leaked (a bare `ThreadPoolExecutor` worker does NOT self-terminate after one task; it blocks for more work until `shutdown()` is called, so omitting this leaks one worker per composed pool). No executor join is allowed to exceed `remaining()`; neither `shutdown(wait=False)` call blocks.

**Session RPC over the raw transport (R-1, R-3b).** Because the pool issues `session.create`/`session.resume` on the RAW transport (not `GatewayChild.request`), it does a tiny **synchronous request/response over the transport** for exactly these two pool-owned calls, using the ONE PERMANENT `on_frame` callback that is already routing to the relay. The permanent callback FIRST feeds a per-child `PoolSessionResponder` — but the responder **OBSERVES** the matching response (unblocks the waiter) and does **NOT** consume or suppress it from the ordered routing (R-1, R-7): the frame still flows on to the relay in ingress order and is fanned out to that employee's subscribers (R3-D). There is no callback swap. The pool allocates the session-RPC request id from the **relay's id space for that child** (`relay.next_child_request_id(generation)`, §4) so pool ids never collide with downstream-forwarded ids; it enqueues the frame via `transport.enqueue_frame`, and blocks (off-loop, in the init executor) on `(responder.done OR transport.dead_event)` up to the request timeout (R-3b — a child death wakes it immediately). This keeps ALL blocking off the loop (§0) and keeps ONE ordered ingress (§0).

    3. If we own the slot: perform the ENTIRE blocking spawn OFF the lock — first, if a dead record exists, **fully shut down the stale transport** within `CHILD_CLEANUP_BUDGET_SECONDS` before replacing it (R-8 — `alive=False` is stdout EOF, not process reap; explicitly `close_stdin → wait → kill → join` so an old process cannot outlive its replacement resuming the same stored session), then `_spawn_and_bind(employee_entity_id, slot)`. `_spawn_and_bind` publishes the partial `transport`+`generation` into `slot` the instant `spawn` returns a transport (R3-B), BEFORE `wait_ready`/session-RPC.     4. **Publish/discard under `_lock`** (short, R3-B): **RE-CHECK `_closing` first.** If `_closing` is set (shutdown began during this spawn), do NOT insert into `_records`; instead set `slot.error` to a transport error, pop the slot, `slot.done.set()`, release the lock, and — off the lock — boundedly shut down the just-built transport (within `CHILD_CLEANUP_BUDGET_SECONDS`) and `relay.unregister_child(generation)`, so a spawn that finishes after shutdown can NEVER re-add a live child to `_records`. Otherwise (not closing): on success, insert into `_records` and set `slot.record`; on failure set `slot.error`; in both cases pop the slot from `_init_slots` and `slot.done.set()`. Release. Then return the record or raise the error.
    (Different employees never contend beyond the microsecond dict-mutation windows; the same employee's concurrent callers coalesce onto one spawn. `shutdown` can always acquire `_lock` promptly because nothing blocking is ever held under it — R-2. A shutdown that races a publish is resolved by the re-check: either the publish sees `_closing` and discards, or shutdown sees the record in `_records` and tears it down — never both leave a live orphan — R3-B.)

    1. construct transport (reader NOT started); **immediately publish `slot.transport = transport` and `slot.generation = generation` under `_lock`, AND in that SAME locked section re-check `_closing`** (R3-B, R3-round3-1): if `_closing` is already set, do NOT proceed to steps 2-5 — release the lock, boundedly `transport.shutdown(...)` the just-built transport, and raise a transport error (the caller records it in the slot and `slot.done.set()`s). This closes the window Codex flagged where `shutdown` snapshots the slot while `slot.transport is None`: the owner cannot start/RPC an already-closing child, because it re-checks `_closing` at the exact moment it makes the transport visible. If not closing, publish and continue,
    2. `relay.register_child(generation, employee_entity_id, transport)` (binding + id space exist BEFORE any frame),
    3. `transport.start_reading()` (stdout reader begins; the first frame — `gateway.ready` — now routes through the live binding and reaches subscribers, R-3),
    4. `transport.wait_ready(ready_timeout)` (reads frames through the same permanent callback; `gateway.ready` both opens the gate AND is forwarded, R-1/R-3),
    5. `_create_or_resume_session(...)` (the pool issues `session.create`/`session.resume`; the responder OBSERVES its response id to unblock, and that response ALSO flows to the relay and is fanned out to subscribers per §5/R3-D),
    6. return the record (publication into `_records` happens in `child_for_employee` step 4, under the `_closing` re-check).
    If any step 2-5 raises, the caller (`child_for_employee`) boundedly tears the transport down and, if registered, `relay.unregister_child(generation)` so no stale binding leaks.
  - `_env_for_employee(self, employee_entity_id: str) -> dict[str, str]` — the EXACT identity env: `env = dict(self._base_env)`; **explicitly `env.pop("PLAN_TICKET_ID", None)` and `env.pop("HERMES_TUI_SKILLS", None)`** to strip any inherited role/skill/ticket identity BEFORE setting the employee-specific keys (production passes `os.environ`, which may carry a stale ticket id — a chief child must never inherit one). Then set `HERMES_PYTHON_SRC_ROOT`, `HERMES_HOME`, and the identity keys (§6).
  - `_create_or_resume_session(self, transport, employee_entity_id, generation) -> str` — returns `stored_session_id`. Fresh spawn (no held `stored_session_id`): issue `session.create {source: RELAY_SESSION_SOURCE, cols: SESSION_COLS}` via `_transport_request`; read `stored_session_id`. Respawn (a held pool-created `stored_session_id`): issue `session.resume {session_id: stored_session_id}`. It NEVER resumes an id it did not itself create.
  - `_transport_request(self, transport, generation, method, params, timeout) -> JsonDict` (R-1, R-3b, R3-D) — the pool-owned synchronous RPC over the raw transport: allocate a child-facing id from the relay's id space for `generation` (`relay.next_child_request_id(generation)`); install a `PoolSessionResponder` keyed by that id as an OBSERVER on the permanent callback (it captures the matching response WITHOUT suppressing routing — R3-D); `transport.enqueue_frame({"jsonrpc":"2.0","id":rid,"method":method,"params":params})`; block on `(responder.done OR transport.dead_event)` up to `timeout` (R-3b); return the response `result` dict, or raise a transport error on timeout / child death / an RPC error frame. Runs off-loop (inside `child_for_employee`, itself in the init executor). The observed response frame ALSO reaches the relay and is fanned out to the employee's subscribers (§5/R3-D).
  - `shutdown(self, *, deadline: float) -> None` (R-2, R-3d, R3-A, R3-B, R3-G) — **keyword-only; MUST be called via `functools.partial(pool.shutdown, deadline=deadline)` when scheduled through `run_in_executor` (R3-A).** **Mark closing and snapshot under the short lock, then tear down OFF the lock, on the reserved shutdown path (R3-G).** Under `_lock`: set `_closing = True`; snapshot `active = list(self._records.values())`; snapshot `in_progress = list(self._init_slots.values())`; clear `_records`. Release the lock. Off the lock: for each active record, `record.transport.shutdown(deadline=deadline)`; **for each in-progress slot: if `slot.transport` is already published (R3-B), directly `slot.transport.shutdown(deadline=deadline)` — the `kill()` unblocks that spawn's `wait_ready`/`_transport_request` immediately — then, if `slot.generation` was registered, `relay.unregister_child(slot.generation)`. If `slot.transport is None` at snapshot time (the spawn owner has not yet reached the publish point), do NOT spin — the owner's publish-time `_closing` re-check (R3-round3-1) guarantees it will see `_closing` and abort BEFORE starting/RPC-ing the child, so just wait bounded on `slot.done` within remaining. In BOTH cases wait bounded on `slot.done`** (the owner's own bounded cleanup also runs, and the publish-time `_closing` re-check guarantees it will NOT insert a live record — R3-B, R3-round3-1). Then shut the pool's OWN executors down within remaining (R3-G): `self._init_executor.shutdown(wait=False, cancel_futures=True)` (killed transports unblock their threads on EOF); and as the LAST action, `self._shutdown_executor.shutdown(wait=False, cancel_futures=True)` (R3-round3-4) — safe from its own worker (`wait=False` marks it shut and the single worker exits once this `pool.shutdown` returns), so the reserved worker is reclaimed rather than leaked. Aggregate the first exception, finish the rest, re-raise last (mirror `EntityRoutingGateway.shutdown`, shared_gateway.py:156-170). Every `wait`/`join` is bounded by `remaining()` against the ONE deadline, so this returns bounded even if an init executor thread is still alive when the deadline expires (R-3d): `transport.shutdown` has already reached `kill()`, the init thread's blocking child read/wait unblocks on the resulting EOF, and any residual join is bounded — the loop (which awaits this via `run_in_executor(pool.shutdown_executor, ...)`) never hangs. No blocking call runs under `_lock`.

### `employee_child_relay.py` — the relay core

Purpose: owns the per-child id table; namespaces downstream request ids onto each child's own integer id space; routes each child's frames only to downstreams subscribed to that child's employee; correlates responses back to origin; fans out EVERY uncorrelated employee-scoped frame (R3-D); synthesizes a child-reset event frame on child death; carries the tee-observer seam; **rejects downstream session-lifecycle frames with a JSON-RPC error** (R-6) by construction (R-5 denylist).

Module constants:
- `RELAY_CHILD_RESET_CODE: Final = -32010` — the JSON-RPC error `code` the relay puts on a downstream request that cannot complete because its child reset (the death-path completion in `deliver_child_death`, and the R3-C dead-window completion in `_forward`). A single relay-owned code in the JSON-RPC implementation-defined server-error range (`-32000..-32099`), distinct from any Hermes code, so a downstream can recognize a relay-generated child-reset failure. Reused everywhere the relay completes a request due to child death.
- `RELAY_SESSION_LIFECYCLE_REJECTED_CODE: Final = -32011` — the JSON-RPC error `code` for a denied session-lifecycle request (R-6); relay-owned, same range, distinct from the reset code.

Types / records:

- `@dataclass` **`DownstreamConnection`** — one connected browser client.
  - `downstream_id: int` — process-unique, from an `itertools.count` in the relay.
  - `outbound: asyncio.Queue[str]` (R-11 — typed as `str`; the relay serializes frames to text at the moment of routing and enqueues `str`; the route's writer coroutine `send_text`s them directly). Frames waiting to be written to this socket.
  - `subscribed_employee_entity_ids: set[str]` — employees this downstream follows.
  - `pending: dict[tuple[int, int], PendingForward]` — this downstream's in-flight forwards, keyed by `(child_generation, child_request_id)`. The per-downstream O(k) index for disconnect cancel; shares the key space with restoration.

- `@dataclass` **`PendingForward`** — one forwarded, not-yet-answered request.
  - `downstream_id: int`
  - `child_generation: int`
  - `child_request_id: int`
  - `downstream_request_id: Any` — the original id as it appeared on the downstream wire (kept opaque — int or str per JSON-RPC).
  - (No `handle`, no `GatewayChild` reference.)

- `@dataclass` **`ChildBinding`** — one live child the relay routes for.
  - `child_generation: int`
  - `employee_entity_id: str`
  - `transport: RawFrameChildTransport`
  - `next_request_id: int` — the child-facing id counter, starts at 1, incremented under `_lock` (§4). The relay OWNS this id space.
  - `pending_by_child_request_id: dict[int, PendingForward]` — this child's in-flight forwards keyed by the id the relay assigned; the restoration lookup.

- **`EmployeeChildRelay`**:
  - `__init__(self, *, pool_provider: Callable[[], EmployeeChildPool | None], loop: asyncio.AbstractEventLoop, tee_observers: Sequence["RelayTeeObserver"] = ())`.
    - `pool_provider` — zero-arg callable returning the pool (or None); a lambda over `app.state`, the composition seam the config-gate test drives.
    - `tee_observers` — the tee seam; S1 passes TEST observers only.
    - (Dropped `request_timeout` — the relay never consumes it; the pool owns request timeouts. R-12.)
  - `_downstreams: dict[int, DownstreamConnection]`
  - `_subscribers_by_employee: dict[str, set[int]]` — employee → set of downstream_ids (the O(1) routing index).
  - `_children: dict[int, ChildBinding]` — child_generation → binding (the pool registers each spawned child here via `register_child`).
  - `_lock: threading.Lock` — a plain `threading.Lock`, NOT an `asyncio.Lock`. Chosen because the delivery callbacks (`deliver_child_frame`/`deliver_child_death`) are plain synchronous functions that cannot `await` a lock, and because the relay maps are read/written both on the loop (subscribe/forward, delivery callbacks scheduled via `call_soon_threadsafe`) and off the loop (the pool's `register_child`/`next_child_request_id`/`unregister_child` run in the init executor during `child_for_employee`). Critical sections are short (dict mutations + snapshotting a recipient list); no `await` ever happens while holding it, and no blocking pipe I/O happens under it (enqueue to the transport's outbound queue is non-blocking `put_nowait`).
  - `register_child(self, generation, employee_entity_id, transport) -> None` / `unregister_child(self, generation) -> None` / `next_child_request_id(self, generation) -> int` — pool-facing (called off-loop in the init executor). `register_child` inserts the `ChildBinding` under `_lock` (called in step 2 of `_spawn_and_bind`, BEFORE `start_reading` — R-1). `unregister_child` removes it (on a failed bind or a closing-race discard). `next_child_request_id` returns and increments `binding.next_request_id` under `_lock`.
  - `_binding_alive_locked(self, generation) -> bool` (R3-C, R3-round3-3) — the NON-LOCKING core: assumes the caller ALREADY holds `_lock`; returns whether `generation` is still in `_children` AND its transport is `alive`. This is what `_forward` calls inside its own `_lock` critical section (§4 step 0) — calling a lock-acquiring helper while already under the non-reentrant `_lock` would self-deadlock (R3-round3-3).
  - `binding_alive(self, generation) -> bool` (R3-C) — the public lock-acquiring wrapper: `with self._lock: return self._binding_alive_locked(generation)`. Used only by callers that do NOT already hold `_lock`. `_forward` must use `_binding_alive_locked` (it is already under the lock), NOT this wrapper.
  - `register_downstream(self) -> DownstreamConnection` / `unregister_downstream(self, conn) -> None` — add/remove from `_downstreams`, drop the connection from `_subscribers_by_employee`, and **cancel all and only this downstream's pending forwards** by iterating `conn.pending.values()` (O(k)), removing each from its child's `pending_by_child_request_id`. (No response is emitted to a gone downstream — its socket is closed; the entries are simply dropped, freeing the child id table.) Spans every child this downstream touched (each `PendingForward` carries its own `child_generation`).
  - `handle_downstream_message(self, conn, raw_text: str) -> Awaitable[None] | None` — the discriminator (§3): parse JSON; if `"relay" in obj` → control message (`subscribe` updates subscriptions; `request` is a forward). For a forward: read `employee_entity_id`, extract the inner `frame`. **Session-lifecycle guard (R-5, R-6):** if the inner frame's `method` is in `SESSION_LIFECYCLE_DENYLIST` (§3), answer the downstream with a **JSON-RPC error response** `{"jsonrpc":"2.0","id":<inner id>,"error":{"code":RELAY_LIFECYCLE_DENIED_CODE,"message":"session lifecycle is pool-owned"}}` (R-6) and DO NOT touch any child. Otherwise resolve employee→child via the pool (spawn on demand, off-loop) and forward (below). Notify tee (`FROM_DOWNSTREAM_TO_CHILD`, labeled with employee).
    - Because employee→child resolution can spawn (blocking, §0/R-3), the forward is an `async def _forward(conn, employee_entity_id, inner_frame)` coroutine the route schedules as a TRACKED task (R-3a): `record = await loop.run_in_executor(pool.init_executor, pool.child_for_employee, employee_entity_id)` (on the pool's dedicated init executor — R3-G); then on the loop, **under `_lock`, FIRST re-validate the binding** (R3-C): confirm `record.child_generation` is still in `_children` and its transport is `alive` via `self._binding_alive_locked(generation)` (the NON-locking variant, because `_forward` already holds `_lock` — calling the lock-acquiring `binding_alive` here would self-deadlock the non-reentrant lock, R3-round3-3); **if the child already died in the window between resolution and registration, do NOT register any pending and do NOT enqueue — instead complete the downstream request EXACTLY ONCE with a JSON-RPC error of the same shape as the death path** `{"jsonrpc":"2.0","id":<downstream id>,"error":{"code":RELAY_CHILD_RESET_CODE,"message":"child reset before responding"}}` and return (no untracked task, no orphan pending — R3-C). Only for an id-less inner frame (a notification, which has no id to answer) the dead-window case drops silently. Otherwise (binding alive): allocate `child_request_id = binding.next_request_id (++)`, register the `PendingForward` in BOTH `binding.pending_by_child_request_id` and `conn.pending`, rewrite `frame["id"] = child_request_id`, and `transport.enqueue_frame(frame)` — **validation, id allocation, and enqueue happen together under the lock so a death cannot slip between the alive-check and the enqueue, and enqueue order == allocation order** (R-9/R3-C; the single writer thread then preserves it on the wire). Id-less inner frames (notifications) are enqueued verbatim, no id rewrite, no pending entry. On a spawn/resolution failure (before any pending is registered), emit a JSON-RPC-shaped error back to the downstream (the SINGLE owner of that failure completion — see R-8 below). The receive loop stays responsive because `_forward` runs as its own task.
  - `deliver_child_frame(self, generation: int, frame: JsonDict) -> None` — **on the loop**, scheduled by the transport's reader thread. Under `_lock` resolve the `ChildBinding` for `generation`; if the child is gone (already retired), drop the frame. Classify (R3-D):
    - **Correlated response** — `id` present AND (`result` in frame or `error` in frame) AND `binding.pending_by_child_request_id` HAS `frame["id"]`: pop the `PendingForward` (and from `conn.pending`); rewrite ONLY the top-level `id` back to `pending.downstream_request_id`, leaving every other field verbatim (error frames pass through verbatim — no synthetic error schema; R-11 structural); serialize to text and enqueue to the origin downstream's `outbound`; notify tee (`FROM_CHILD_TO_DOWNSTREAM`).
    - **Uncorrelated / employee-scoped frame — EVERYTHING else, fanned out (R3-D).** An id-less notification/event, a `gateway.ready` process frame (R-3), an `id:null` parse-error response (entry.py:362), OR an id-bearing response with NO matching pending (including a pool-issued `session.create`/`session.resume` response, whose id is in the relay's id space but has no downstream origin): **ALL of these are fanned out to that employee's subscribers in ingress order and tee'd.** No unmatched response is dropped (R3-D). Rationale: the contract requires every child frame to remain employee-scoped and visible (contract:71,83); and `ChildBinding` carries no pool-request-id registry that could reliably distinguish a pool response from any other unmatched response, so a "drop pool responses" rule is both unimplementable-cleanly and contract-noncompliant. The pool's `PoolSessionResponder` still OBSERVES its matching response to unblock the waiter, but it NEVER suppresses routing — the frame flows through here and is fanned out like any other uncorrelated frame. Snapshot the subscriber set for `binding.employee_entity_id` under `_lock`, release, serialize, `put_nowait` the frame text to each recipient's `outbound`; notify tee.
    Never rewrites payload beyond the one top-level id (on the correlated-response branch only).
  - `deliver_child_death(self, generation: int) -> None` — **on the loop**. Under `_lock`: look up the `ChildBinding` for `generation`; if absent (already retired), return (dedup — R-4/generation keying). Otherwise remove the binding, snapshot its subscribers, and gather all `PendingForward`s in `binding.pending_by_child_request_id`. Release the lock. **This is the SOLE owner of failure completion for that child's pendings (R-8):** for each pending, build a JSON-RPC-shaped error response `{"jsonrpc":"2.0","id":<downstream id>,"error":{"code":RELAY_CHILD_RESET_CODE,"message":"child reset before responding"}}`, serialize, enqueue to the origin downstream, and drop it from `conn.pending`. Then synthesize and enqueue the child-reset event frame (§5) to each subscriber. Notify tee. Only THIS generation's mappings are touched.

    **R-8 (no double-completion on failed write).** A failed `enqueue_frame`/write does NOT complete the downstream request in the `_forward` path. Ownership is single: the write failure triggers `transport._mark_dead()` → `deliver_child_death(generation)`, which emits the SOLE error for every one of that child's still-registered pendings (including the one whose send just failed). `_forward`'s send path does NOT emit a per-request error on a write failure; it registers the pending under the alive-check and enqueues, and if the child is already dead the death path owns completion. The TWO places `_forward` emits a direct error are (i) a **spawn/resolution failure** (before any pending is registered) and (ii) the **dead-window case** (R3-C — resolution succeeded but the binding died before registration, so no pending exists and no death path will fire for this request) — in both, there is no pending and no competing death completion, so there is exactly one completion per request in every case (tested in §8: exactly one response reaches the downstream).

    Note: the pool retires the dead POOL record lazily on the next `child_for_employee`; the RELAY retires its `ChildBinding` immediately here. Both are keyed by generation, so a delayed old death after respawn hits the retired old generation and is a no-op.

  - `subscribe(self, conn, employee_entity_ids) -> None` — replace `conn.subscribed_employee_entity_ids` with the new set and rebuild that connection's slots in `_subscribers_by_employee`, all under `_lock`.

### `relay_route.py` — the downstream FastAPI WS route

Purpose: the one downstream WebSocket route; same auth posture as `/api/events` (middleware-only). Mirrors `tail_events`'s structure (accept, spawn a watcher, writer loop, cleanup), and — per R-3a/R-10 — **terminates and unregisters when EITHER the receive side or the writer side ends**, tracking in-flight `_forward` tasks so teardown drains them.

- `async def relay_downstream_websocket(websocket, *, pool_provider, relay, unavailable_close_code: int = 1013) -> None`:
  - If `pool_provider()` is None (backend off/unavailable): `await websocket.accept()` then `await websocket.close(code=1013, reason="relay backend unavailable")` and return (accept-then-close so the client sees a clean 1013, matching `tail_events`).
  - Else: `await websocket.accept()`; `conn = relay.register_downstream()`; maintain a `pending_forwards: set[asyncio.Task]` (R-3a); start a **writer task** that loops `text = await conn.outbound.get(); await websocket.send_text(text)`; run the **receive loop** `raw = await websocket.receive_text()`, handing each to `relay.handle_downstream_message(conn, raw)` and, when that returns a `_forward` coroutine, wrapping it in a task added to `pending_forwards` (with a done-callback that discards it). Use `asyncio.wait({receive_task, writer_task}, return_when=FIRST_COMPLETED)` so that **when the writer task raises from `send_text` (R-10 writer-side) OR the receive side hits `WebSocketDisconnect` (R-10 receive-side)**, the whole handler tears down: cancel the other task and all outstanding `pending_forwards`, `await` their settle (stops admitting new work before unregister — R-3a), then `relay.unregister_downstream(conn)` in `finally`. This guarantees a dead socket never leaves the receive side, the writer, or any in-flight forward parked, from EITHER side (R-10). Mirrors `tail_events`'s bounded watcher/cleanup discipline.

```python
    if not config.relay_backend_enabled:
        return None
    relay = EmployeeChildRelay(pool_provider=lambda: app_state.employee_child_pool, loop=loop)
    pool = EmployeeChildPool(
        hermes_python=hermes_python, planner_home=planner_home, base_env=base_env,
        relay=relay, loop=loop, spawn=spawn,
    )
    app_state.employee_child_pool = pool
    app_state.employee_child_relay = relay
    return pool
```

Returns the pool (or None) so `_lifespan` captures it into its `*_to_shutdown` local for the `finally` off-loop shutdown (§7). This is the only import site for `EmployeeChildPool`/`EmployeeChildRelay`; `server.py` does NOT import them directly (R-12).

## 3. Downstream subscribe message shape (and the discriminator) + session-lifecycle guard

The relay connection carries two kinds of downstream→relay text frames: relay-control messages and native JSON-RPC requests to forward. The relay tells them apart WITHOUT parsing native Hermes semantics, and a forwarded request ADDRESSES an employee.

**Discriminator: a top-level `"relay"` key.** Every relay-control message is a JSON object with a top-level `"relay"` string naming the verb. Native JSON-RPC requests never carry a top-level `"relay"` key. Rule: parse the text; if it is an object and `"relay" in obj`, it is a control message; otherwise (defensively) treat it as a bare native frame — but the S1 contract routes all forwards through the `{relay:"request", ...}` envelope, so a bare native frame with no envelope is answered with a relay-control error (it has no employee address). Justification: `"relay"` is a namespace JSON-RPC 2.0 does not use, so the discriminator is unambiguous and interprets no native payload.

**Subscribe control message:**

```json
{ "relay": "subscribe", "employee_entity_ids": ["<entity-id>", "..."] }
```

- Sets `conn.subscribed_employee_entity_ids` to exactly this set (replace semantics — declarative, idempotent) and rebuilds `_subscribers_by_employee`. Empty list unsubscribes from all. Subscribe does NOT spawn children (spawn is on first forwarded request addressing the employee); it primes routing.

**Addressing an employee on a forwarded request — an envelope the relay strips:**

```json
{ "relay": "request", "employee_entity_id": "<entity-id>", "frame": { "jsonrpc": "2.0", "id": 7, "method": "prompt.submit", "params": { ... } } }
```

- The relay reads `employee_entity_id` (addressing), then forwards the INNER `frame` verbatim to that employee's child — rewriting ONLY the inner frame's top-level `id` onto the child's id space (§4). Everything else passes through untouched. The envelope is stripped; the child never sees `relay`/`employee_entity_id`.
- Id-less inner frames (notifications) forward verbatim, no id rewrite, no pending entry.

Any object with `"relay"` not in `{"subscribe","request"}` is answered with `{ "relay": "error", "detail": "unknown relay verb", "verb": <v> }` enqueued to that downstream (touches no child).

### Session-lifecycle guard (R-5 — the pool is the sole session-lifecycle issuer; R-6 — JSON-RPC rejection)

The relay does NOT forward downstream-originated session-lifecycle frames to any child. The denylist has **NINE** members: the six `session.*` binding methods PLUS three generic lifecycle escape hatches (`handoff.request`, `cli.exec`, `slash.exec`) verified against the real `tui_gateway` registry.

```python
SESSION_LIFECYCLE_DENYLIST: Final[frozenset[str]] = frozenset({
    # The six session.* binding methods (mint / rebind / destroy session ownership):
    "session.create",   # mints a new session
    "session.resume",   # binds/reattaches ownership of a stored session
    "session.branch",   # mints a new session from an existing one
    "session.activate", # rebinds the live frontend focus to another session
    "session.close",    # tears down session ownership
    "session.delete",   # destroys a stored session
    # Three generic lifecycle escape hatches (deny WHOLESALE — S1 parses no payloads):
    "handoff.request",  # writes handoff_state=pending; a separate `hermes gateway` process
                        # re-binds this session to a platform channel (server.py:6323-6330) —
                        # a session rebind that breaks own-session ownership.
    "cli.exec",         # runs arbitrary `python -m hermes_cli.main` argv (server.py:11737);
                        # _cli_exec_blocked (11721) only stops setup/gateway/sessions-browse/
                        # config-edit, so `sessions delete` and session-minting CLI verbs pass —
                        # reaches session destroy/mint indirectly.
    "slash.exec",       # runs an arbitrary slash command through a resumed _SlashWorker
                        # (server.py:13049); /new, /resume, /branch are lifecycle commands —
                        # reaches session mint/rebind indirectly.
})
```

When a `{relay:"request"}` inner frame's `method` is in `SESSION_LIFECYCLE_DENYLIST`, the relay answers the downstream with a **JSON-RPC error response** (R-6), NOT a relay-control frame:

```json
{ "jsonrpc": "2.0", "id": <original inner id>, "error": { "code": <RELAY_LIFECYCLE_DENIED_CODE>, "message": "session lifecycle is pool-owned" } }
```

and NEVER writes to the child. `RELAY_LIFECYCLE_DENIED_CODE` is a stable module constant (a fixed negative integer in the JSON-RPC application-error range, e.g. `-32040`; documented once). Answering on the original inner id means a native JSON-RPC client waiting on that id sees completion (R-6). If the inner frame has NO id (a lifecycle *notification* — no id to answer), the relay drops it silently (there is no id to complete). **`{relay:"error"}` is retained ONLY for malformed relay ENVELOPES** (unknown verb, missing address, un-parseable envelope) — cases with no inner JSON-RPC id to answer (R-6).

This preserves the one-child-one-session / own-session-only invariant BY CONSTRUCTION: a browser cannot mint a second session on a child, cannot resume a role-child's session, cannot destroy the pool's session, and cannot reach any of those goals through the three generic escape hatches. **Every other native method flows verbatim** — this is a denylist, not an allowlist. Same-session, non-binding operations forward untouched: `prompt.submit`, `clarify.respond`, `session.interrupt`, `session.steer`, `session.compress`, `session.cwd.set` (a same-session mutation — correctly OFF the denylist, R-5), `approval.respond`, `command.dispatch`, `session.status`, `session.history`, `session.title`, `session.usage`, `session.save`, `session.undo`, `session.list`, and any other verb.

**Registry inventory (corrected; R-5).** Inspecting the tui_gateway `@method("session.*")` registry (`~/.hermes/hermes-agent/tui_gateway/server.py`), there are **20** registered `session.*` methods (the prior draft said 19 — it missed `session.cwd.set`, which correctly stays OFF the denylist as a same-session mutation). The 20 are: `session.activate, session.active_list, session.branch, session.close, session.compress, session.context_breakdown, session.create, session.cwd.set, session.delete, session.history, session.interrupt, session.list, session.most_recent, session.resume, session.save, session.status, session.steer, session.title, session.undo, session.usage`. Exactly six of those twenty (`create/resume/branch/activate/close/delete`) mint/rebind/destroy session ownership; the other fourteen are read-only or same-session and forward. The three generic escape hatches (`handoff.request`, `cli.exec`, `slash.exec`) are NOT `session.*` methods but reach session mint/rebind/destroy indirectly, so they are added to the denylist for a total of **9**.

**Maintained registry snapshot + mechanically-derived completeness test (R-5, R3-E).** A module constant records the KNOWN upstream registry, and the completeness test (§8) does NOT compare two hand-written literals — it **mechanically scans the installed `tui_gateway/server.py` `@method("...")` decorators** (a static file read; no live Hermes process) and asserts the recorded snapshot still matches, so a 21st upstream `session.*` (or lifecycle) method FAILS the test until the snapshot is deliberately refreshed:

```python
# The maintained snapshot of the installed tui_gateway registry.
# Source of truth: the @method("...") decorators in tui_gateway/server.py.
# The completeness test scans those decorators from the file and FAILS if this
# snapshot drifts (e.g. an upstream checkout adds a 21st session.* method),
# forcing a conscious re-derivation and denylist re-check.
KNOWN_TUI_GATEWAY_SESSION_METHODS: Final[frozenset[str]] = frozenset({ ... the 20 above ... })
KNOWN_TUI_GATEWAY_LIFECYCLE_CAPABLE: Final[frozenset[str]] = frozenset({
    # the binding-capable subset that MUST be denied, drawn from the known registry:
    "session.create", "session.resume", "session.branch",
    "session.activate", "session.close", "session.delete",
    "handoff.request", "cli.exec", "slash.exec",
})
```

**How the scan works (R3-E — static file read, no live process).** The test locates the installed `tui_gateway/server.py` (the same checkout the runtime uses; path derived from `resolve_hermes_python()`/`hermes_src_root()` or an explicit env, resolved once and skip-guarded with a clear message if absent so `./verify` never hard-fails on a missing checkout), reads it as TEXT, and extracts every method name from the `@method("...")` decorators via a small regex/scan (e.g. all string literals inside `@method(...)`). From that extracted set it derives `scanned_session_methods = {m for m in scanned if m.startswith("session.")}`. The test then asserts:
   (a) `scanned_session_methods == KNOWN_TUI_GATEWAY_SESSION_METHODS` — a 21st (or removed) `session.*` decorator in the file makes this FAIL until the snapshot is refreshed (this is the drift trip-wire, R3-E);
   (b) `SESSION_LIFECYCLE_DENYLIST ⊆ scanned_registered_methods` for the members that ARE registered methods, and `KNOWN_TUI_GATEWAY_LIFECYCLE_CAPABLE ⊆ SESSION_LIFECYCLE_DENYLIST` (the known binding-capable subset is fully denied);
   (c) the six `session.*` binding members of the denylist are exactly `KNOWN_TUI_GATEWAY_SESSION_METHODS ∩ SESSION_LIFECYCLE_DENYLIST` and number six;
   (d) `session.cwd.set ∈ scanned_session_methods AND session.cwd.set ∉ SESSION_LIFECYCLE_DENYLIST` (a same-session mutation stays forwardable).
Because the check DERIVES the `session.*` set by scanning the actual decorators, a future upstream method addition surfaces as a test failure (not a silent pass), which is exactly what R3-E requires — no live Hermes process is needed. Justification (per "Decisions the contract left open"): the contract says the pool "creates fresh sessions or resumes only sessions it created" and "never lets two children own the same stored session" — enforceable only if session lifecycle is pool-owned, and the three generic escape hatches must be denied wholesale or the six-method guard is bypassable.

## 4. Id-namespacing per child + concurrency (relay-owned id space)

**One id space per child, owned by the relay.** Because the relay writes the raw frame to the child, IT chooses the child-facing id. Each `ChildBinding` owns `next_request_id` (starts at 1, incremented under `_lock` in `next_child_request_id(generation)`). When forwarding a downstream request the relay, **all under one `_lock` critical section** (so the alive-check, allocation, and enqueue are atomic — R3-C, R-9): (0) **re-validate the binding is present and alive via `_binding_alive_locked(generation)`** (R3-C, R3-round3-3 — the NON-locking helper, since this whole block is already inside the `_lock` critical section; the child may have died in the window between `child_for_employee` returning and this point; if dead, complete the request exactly once with a `RELAY_CHILD_RESET_CODE` JSON-RPC error and register NOTHING); (1) take the inner frame's original top-level id (`downstream_request_id`, opaque); (2) allocate `child_request_id = binding.next_request_id` and increment; (3) rewrite `frame["id"] = child_request_id`; (4) register a `PendingForward` in BOTH `binding.pending_by_child_request_id[child_request_id]` and `conn.pending[(child_generation, child_request_id)]`; (5) `transport.enqueue_frame(frame)` — the enqueue happens in the same critical region as the alive-check and allocation, so no death can slip between validation and enqueue, and the per-child outbound queue receives frames in strictly increasing id order, which the single outbound writer thread (§1) preserves on the wire.

The pool's `session.create`/`session.resume` allocate from the SAME `next_child_request_id(generation)`, so the child sees ONE coherent, strictly-increasing id sequence across pool-issued and downstream-forwarded requests — no gaps, no dupes.

**Death-between-resolution-and-registration (R3-C).** After `pool.child_for_employee` returns a record, but before `_forward` registers its pending, the child can die (its writer thread hits BrokenPipe, or its stdout hits EOF, scheduling `deliver_child_death` on the loop). The under-`_lock` re-validation in step (0) closes this window: because `deliver_child_death` also runs on the loop and takes `_lock`, and because `_forward`'s validate+allocate+register+enqueue is one `_lock` critical section, either (i) death runs first and retires the binding, so `_forward` sees it gone and completes the request EXACTLY ONCE with the reset error (no pending registered, so the death path has nothing to double-complete), or (ii) `_forward` runs first and registers the pending, so the later `deliver_child_death` finds and completes it EXACTLY ONCE. There is no interleaving that leaves an orphan pending, an untracked task, or a request with zero or two completions (R3-C). An id-less inner frame in case (i) is dropped silently (no id to answer).

**Wire-order guarantee (R-9 — choice (a)).** The prior draft claimed strict `[1,2,3]` wire order but sent each frame via an independent `run_in_executor(None, transport.send_frame)`, where two executor threads could acquire the send lock in the reverse of allocation order — the lock prevents only partial-line interleaving, not reordering. **This revision adopts option (a): a single per-child outbound writer thread draining one FIFO queue** (§1). Allocation-and-enqueue is atomic under `_lock`, and the single writer drains FIFO, so the child observes ids in strict allocation order `[1,2,3,...]` (the `session.create` id is 1, then each forward). The `[1,2,3]` claim is kept AND the raw pipe write is serialized off-loop by construction (also satisfying R-3c). The §8 test asserts `fake.sent` request ids are exactly `[1,2,...]` in order.

**Restoration (R-6-round-1 / cross-child no-collision).** When a response frame arrives on the ordered ingress for `generation`, the relay reads `frame["id"]` and pops `binding.pending_by_child_request_id[frame["id"]]` → `PendingForward`. It rewrites the top-level id back to `pending.downstream_request_id` and enqueues to `pending.downstream_id`'s `outbound`. **The restoration key is `(child_generation, child_request_id)`**, never the bare downstream id — so one downstream issuing id `1` concurrently to two different employees (two children, two generations) creates two DISTINCT pending entries `(genA,1)` and `(genB,1)` that never collide. A response id that has NO matching pending (a pool-issued session response, or any other unmatched id-bearing response) is an uncorrelated employee-scoped frame per §5/R3-D — fanned out to that employee's subscribers and tee'd, never dropped.

**Per-downstream O(k) disconnect cancel.** `conn.pending` keyed by `(child_generation, child_request_id)` indexes ALL of one downstream's in-flight forwards across EVERY child it touched. On disconnect the relay iterates `conn.pending.values()` (O(k)), removing each from its child's `pending_by_child_request_id` and dropping the entry — cancelling ONLY this downstream's mappings, across all its children.

**Locking discipline (explicit).** ONE `threading.Lock` (`self._lock`) guards ALL relay maps and each binding's `next_request_id` + `pending_by_child_request_id`, each conn's `pending` on structural mutation. A `threading.Lock` (not `asyncio.Lock`) because the delivery callbacks are plain synchronous and the pool touches relay maps off-loop. Critical sections are short dict ops + a recipient snapshot; NO `await` and NO blocking pipe I/O ever happens while holding it (the enqueue is a non-blocking `put_nowait` onto the transport's outbound queue, done inside the same short critical region as allocation).

**Concurrent interleaved requests, same child, two downstreams.** A and B each forward to the same employee. Each validate-allocate-enqueue is serialized under `_lock`, so A and B get distinct child ids AND the child sees them in allocation order; each response restores by `(generation, child_request_id)` to its own origin. The concurrency test uses a barrier fake (§8) that returns each send immediately and withholds RESPONSES until both requests are observed.

## 5. Routing

**Employee-scoped, never broadcast.** A child's frames arrive at `deliver_child_frame(generation, frame)` labeled by the child generation → its `ChildBinding.employee_entity_id`. Both session-scoped events AND process-level frames (including `gateway.ready`, no `session_id`, no `id`) travel the SAME ordered ingress and are routed ONLY to `_subscribers_by_employee[employee_entity_id]`. No code path sends a child's frame to a downstream not subscribed to that employee.

**Every uncorrelated child frame is fanned out — nothing dropped (R3-D).** Every child frame that is NOT a mapped response is handled as an employee-scoped frame and fanned out to the employee's subscribers in ingress order, then tee'd:
- id-less notifications/events → fanned out to subscribers, tee'd;
- `gateway.ready` (process frame) → fanned out to subscribers, tee'd (R-3);
- `id:null` parse-error responses (entry.py:362) → fanned out to subscribers, tee'd (they carry real child state);
- id-bearing responses with NO matching pending — INCLUDING pool-issued `session.create`/`session.resume` responses → **fanned out to subscribers, tee'd** (R3-D). No unmatched response is dropped. The relay cannot cleanly distinguish a pool response from any other unmatched response (`ChildBinding` has no pool-request-id registry), and the contract requires every child frame to stay employee-scoped and visible; so the single, contract-compliant, implementable rule is: fan out and tee EVERY uncorrelated frame.

The pool's `PoolSessionResponder` is an OBSERVER, not a sink: it unblocks the pool waiter on the matching id but does NOT consume/suppress the frame from the ordered routing — the frame still reaches `deliver_child_frame`, which fans it out like any other uncorrelated frame. This keeps ONE ordered ingress and never silently loses a genuine child frame (R3-D). (A subscriber that connected before the child was spawned thus sees the full startup sequence — `gateway.ready`, the `session.create` response, then following events — in order; this is asserted by the §8 full-pool ordered-visibility test.)

**Emission order preserved (R-4-round-1).** Responses and events interleave in EXACTLY child stdout order because one reader thread hands them to one PERMANENT `deliver_child_frame` callback in order; there is no separate response waiter or executor race that could reorder a response relative to surrounding events. (The §8 verbatim-order test asserts `events_before → response → events_after` arrive downstream in that exact order through the FULL transport.)

**Responses restore to origin.** Id-bearing responses that HAVE a matching pending restore via the `(generation, child_request_id)` lookup (§4); the top-level id is rewritten to the origin downstream's id, every other field preserved verbatim (payload opacity — error frames, error `data`, unknown top-level fields all survive; R-11 structural). Enqueued to that ONE downstream.

**Child-reset event frame (relay-synthesized, employee-scoped).** On child death `deliver_child_death(generation)` builds and enqueues to each subscriber of that employee:

```json
{ "relay": "event", "type": "child_reset", "employee_entity_id": "<entity-id>" }
```

- A relay-control frame (top-level `"relay"`) so downstreams distinguish it from native child frames; labeled with the employee; not a Hermes frame. The "explicit child-reset event frame" the contract requires. No payload beyond the employee identity.

**Payload opacity + the serialization boundary (R-11).** The relay reads/writes only: the discriminator (`"relay"`), the addressing (`"employee_entity_id"`), the envelope wrapper (`"frame"`), the inner request/response TOP-LEVEL `"id"` (namespace/restore), and the inner request `"method"` (ONLY to test denylist membership — §3; never rewritten). It never reads `params` or any nested field and never rewrites nested fields. **"Verbatim" means STRUCTURAL JSON equality modulo the rewritten top-level id** (R-11): the relay round-trips `json.loads` → (rewrite top-level id) → `json.dumps`, which preserves JSON STRUCTURE and unknown fields but NOT bytes/whitespace/escaping/key ordering. The object-envelope design supports exactly this (it carries parsed objects, not original serialized text). The opacity test asserts **structural/deep equality** (unknown nested fields, error `data`, id-less notifications all deep-equal modulo the top-level id), NOT byte-identity (R-11).

**The single serialization point (R-11).** `conn.outbound` is typed `asyncio.Queue[str]`. The relay serializes a frame to text (`json.dumps`) AT THE MOMENT OF ROUTING (in `deliver_child_frame`/`deliver_child_death`/the rejection path) and enqueues the `str`; the route's writer coroutine `await conn.outbound.get()` then `await websocket.send_text(text)` with no further serialization. The transport's egress serializes at `enqueue_frame` (also `json.dumps` → `str` on the outbound queue). One serialization point per direction, `str` everywhere on the queues — consistent across §1/§5/tests (R-11).

**Fan-out mutation-safety and isolation.** In `deliver_child_frame` (fan-out branch) and `deliver_child_death`: under `_lock`, snapshot the recipient set into a list (`recipients = [self._downstreams[i] for i in self._subscribers_by_employee.get(employee, ()) if i in self._downstreams]`); release the lock; then `put_nowait` the serialized text to each recipient's `outbound`. `put_nowait` on an unbounded `asyncio.Queue` never awaits and cannot block. Each `put_nowait`/observer call is wrapped in `try/except Exception` so one bad recipient never aborts the loop or kills the reader. Snapshot-before-release means a concurrent subscribe/unsubscribe cannot mutate the list being iterated. The real `send_text` happens in each downstream's writer coroutine (§1), so a blocked socket cannot stall the reader thread or another downstream — and a writer that raises from `send_text` tears down only its own connection (§1, R-10). (The per-downstream `outbound` queue is unbounded; see "## S1 limitations" for the accepted memory-growth edge and the deferred bounded-queue/overload policy.)

## 6. Child lifecycle

- **Spawn-on-demand.** The first forwarded `request` addressing an employee with no live child calls `pool.child_for_employee(employee_entity_id)` (off-loop, on the pool's dedicated init executor — §0/R-3/R3-G), which spawns. Nothing spawns before demand; with the backend off nothing spawns (pool not composed).
- **Two-phase init ordering (R-1, R3-B).** As detailed in §1's `_spawn_and_bind`: construct transport (reader NOT started) → publish partial `transport`/`generation` into the init slot (R3-B) → `relay.register_child` → `transport.start_reading` → `wait_ready` → session RPC → publish record under `_closing` re-check. The relay binding and id space exist BEFORE any stdout frame is consumed, so `gateway.ready` (emitted by Hermes at entry.py:349, *before* it reads stdin) is never lost and reaches the employee's subscribers.
- **Identity env (exact set).** `_env_for_employee` returns `dict(base_env)` with `PLAN_TICKET_ID` and `HERMES_TUI_SKILLS` EXPLICITLY REMOVED first, then plus:
  - `HERMES_PYTHON_SRC_ROOT = str(hermes_src_root(hermes_python))` — the sys.path hint (same as `shared_gateway._env`).
  - `HERMES_HOME = str(planner_home)` — the configured planner Hermes home.
  - Identity, split by employee kind:
    - **Chief** (`employee_entity_id == chief_entity_id`, i.e. `agent_panels_chief_of_staff`): set `PLAN_ACTOR = "chief"`; do NOT set `PLAN_TICKET_ID` (it was stripped from base_env, so a chief child can never inherit a stale ticket id).
    - **Ticket employee** (any other id): set `PLAN_TICKET_ID = employee_entity_id` (the `_TICKET_ID_ENV` convention, `cli/main.py:27`) and `PLAN_ACTOR = "worker"`.
  - Do NOT set `HERMES_TUI_SKILLS`: role-skill selection is out of S1 scope; it is also stripped from base_env so no inherited skill leaks in.
- **One session per child.** Fresh spawn: `session.create {source: RELAY_SESSION_SOURCE, cols: SESSION_COLS}` → record `stored_session_id`. Respawn of an employee whose pool-created `stored_session_id` is still held: `session.resume {session_id: stored_session_id}`. The pool NEVER resumes a session id it did not create.
- **No idle reaping.** A child lives until pool shutdown or its own death.
- **Dead-child detection (R-4).** The transport's stdout reader observes EOF (`read_stdout()` returns `None`) — the ONLY stdout death signal, since the blocking read never returns on a timeout. A failed outbound write (BrokenPipe) also signals death. Both route through the **atomic single-fire** `_mark_dead()` (a dedicated lock + boolean, returning whether THIS caller won — R-4), so EOF and a failed write can never double-emit even concurrently; only the winner calls `on_dead` → `loop.call_soon_threadsafe(relay.deliver_child_death, generation)`. The relay retires ONLY the `ChildBinding` for that `generation` and cancels ONLY that generation's pending forwards; a delayed old death after respawn hits a retired generation and is a no-op. (The ordering of a final already-emitted stdout frame relative to a write-side death is an accepted S1 edge — see "## S1 limitations".)
- **Respawn shuts down the stale transport first (R-8-round-1).** The pool's record is stale (`transport.alive == False`); the NEXT `child_for_employee` **first fully shuts down the stale transport** (`transport.shutdown(deadline=now+CHILD_CLEANUP_BUDGET_SECONDS)` — the writer closes stdin on the sentinel → wait → kill → join reader/writer threads) because `alive=False` is stdout EOF, not process reap; an old process may still be running and MUST be reaped before a replacement resumes the same stored session. Then it respawns and issues `session.resume {stored_session_id}`.
- **Orphan-free partial init (R-8-round-1, R3-B).** If spawn/`wait_ready`/session-create/session-resume raises, the pool boundedly shuts down the partially-initialized transport (within `CHILD_CLEANUP_BUDGET_SECONDS`) and, if the binding was registered, `relay.unregister_child(generation)`, before re-raising — so no child process and no relay binding is orphaned on a failed spawn. The partial transport is ALSO published into the init slot the instant it exists (R3-B), so `pool.shutdown` can tear it down directly if shutdown begins mid-spawn.
- **Shutdown within the single deadline, off-loop on the reserved path (R-3d, R3-A, R3-B, R3-G).** `pool.shutdown(deadline=deadline)` is called from `_lifespan`'s `finally` via `await loop.run_in_executor(pool.shutdown_executor, functools.partial(pool.shutdown, deadline=deadline))` (R3-A: `functools.partial` because `shutdown` is keyword-only and `run_in_executor` passes positionally; R3-G: on the pool's SEPARATE reserved shutdown executor, never queued behind saturated init work) with the ONE `deadline = _monotonic() + float(config.shutdown_grace_seconds)`. `pool.shutdown` marks `_closing` and snapshots active + in-progress under the short lock, then (off the lock) `transport.shutdown(deadline=deadline)` each active AND each in-progress slot's published partial transport (R3-B), unregistering any registered generation; then shuts the pool's own init executor down within remaining (R3-G). A hung fake child is killed inside `transport.shutdown` when `wait(remaining())` returns None. Because every wait/join is bounded by `remaining()`, the executor call returns bounded even if an init executor thread is still alive when the deadline expires (that thread's blocking child read/wait is unblocked by the `kill()`); the loop never hangs. Shutdown is ordered after the route has stopped forwarding (routes drained on disconnect; `_closing` blocks new spawns and the publish re-check blocks a late insert — R3-B), so no writer thread writes to a killed pipe and no spawn re-adds a live child after closing.

## 11. Decisions the contract left open (each justified in one line)

- **Raw-frame transport instead of `GatewayChild`'s typed methods** — `GatewayChild.begin_request` rebuilds request frames under its own ids and drops unknown fields; `handle.wait()` returns only `result` and RAISES on error; `gateway.ready` is consumed by the readiness gate; and its three separate queues cannot preserve stdout emission order (verified in `gateway.py`). The contract's "through the existing GatewayChild STDIO TRANSPORT" means the `SpawnFn`/`ChildProcess` stdio seam, NOT `GatewayChild`'s client API; ruled in `D-relay-raw-frame-transport`. New code in `hermes_backend/`, so `minds/` is untouched.
- **Two-phase transport init with ONE permanent callback (R-1)** — the transport constructs the reader UNSTARTED; the pool registers the generation with the relay, then calls `start_reading`, so `gateway.ready` (emitted before Hermes reads stdin, entry.py:349) is never delivered before its binding exists and never lost; the single permanent `on_frame` both feeds the pool responder as an OBSERVER and routes every frame to the relay in ingress order — no callback swap, no early-frame consumption.
- **Per-employee init-slot latch carrying the partial transport; no blocking under the global lock (R-2, R3-B)** — a non-reentrant global lock held across spawn/wait/RPC/shutdown would self-deadlock and starve shutdown; instead a per-employee `_InitSlot` coalesces concurrent same-employee spawns while different employees proceed, publishes its partial transport the instant one exists so `pool.shutdown` can tear down a blocked initialization directly, and re-checks `_closing` at publish so a spawn finishing after shutdown never re-adds a live child; the short global lock guards only dict mutations + generation minting + partial-transport publish + the `_closing` flag; shutdown always acquires it promptly.
- **Tracked forwards, death-aware responder waits, dedicated bounded init executor + reserved shutdown path, off-loop deadline-bounded pool shutdown (R-3, R3-A, R3-G)** — the route tracks `_forward` tasks and drains them before unregister; the pool tracks in-progress slots (with partial transports) and refuses new work once `_closing`; the pool responder and `wait_ready` wake on the transport `dead_event` so no executor thread blocks a full timeout; init work runs on the pool's OWN bounded `ThreadPoolExecutor` (so a spawn burst cannot occupy every default-executor worker) and `pool.shutdown` runs on a SEPARATE reserved single-worker executor via `functools.partial(pool.shutdown, deadline=deadline)` (keyword-only, so `functools.partial` is mandatory) — it can never queue behind saturated init work, is internally `remaining()`-bounded, and shuts the pool's own executors within the deadline, so the loop never hangs even if an init thread is still alive at expiry.
- **Single per-child outbound writer thread, sole stdin owner incl. graceful close (R-9, R-3c, R3-G)** — one FIFO queue + one drain thread per child both serializes the raw pipe write off-loop AND preserves allocation order, so the child wire order is strictly `[1,2,3,...]`; the writer thread also closes stdin itself on the shutdown sentinel, so `close_stdin` never races an in-flight `send` on another thread; a mid-`send` blocked write on a wedged pipe is broken by the process `kill()` inside `transport.shutdown` (an accepted S1 edge — see "## S1 limitations").
- **Atomic single-fire death (R-4)** — `_mark_dead` guards the dead transition with a dedicated lock + boolean and returns whether THIS caller won, so concurrent EOF and a failed write fire `on_dead` exactly once (the old `if event.is_set(): return; event.set()` was a race).
- **Death between resolution and pending registration completes exactly once (R3-C)** — `_forward` re-validates the binding is present and alive under the SAME `_lock` critical section that allocates, registers, and enqueues, so a child that dies in the window either is caught by the alive-check (request completed exactly once with a reset error, no pending registered) or the pending is registered before death and completed exactly once by the death path — never an orphan pending, an untracked task, or a zero/double completion.
- **Nine-member lifecycle denylist, JSON-RPC rejection, decorator-scanned completeness test (R-5, R-6, R3-E)** — the six `session.*` binding methods PLUS `handoff.request`/`cli.exec`/`slash.exec` (which reach session mint/rebind/destroy indirectly) are denied wholesale (S1 parses no payloads); a denied native request is answered with a JSON-RPC error on its inner id (so a native client sees completion), while `{relay:"error"}` remains only for malformed envelopes; the completeness test MECHANICALLY SCANS the installed `tui_gateway/server.py` `@method("...")` decorators (a static file read, no live process) and asserts the derived `session.*` set equals the maintained snapshot, so a future upstream 21st method fails the test until the snapshot is refreshed. Registry inventory is 20 `session.*` methods (`session.cwd.set` is the 20th and correctly stays OFF the denylist).
- **Every uncorrelated frame is fanned out and tee'd — nothing dropped (R3-D)** — `id:null` parse-error responses, id-less events, `gateway.ready`, AND unmatched id-bearing responses (including pool-issued session responses) ALL fan out to the employee's subscribers in ingress order and are tee'd; the pool responder observes its matching response to unblock the waiter but never suppresses routing. Dropping pool responses was both unimplementable-cleanly (`ChildBinding` has no pool-request-id registry to distinguish them from any other unmatched response) and contract-noncompliant (every child frame must stay employee-scoped and visible), so the single rule is "fan out and tee every uncorrelated frame" — one ordered ingress, no silent frame loss.
- **One owner of failure completion (R-8, R3-C)** — a write failure triggers death, and generation-death processing emits the SOLE error for all that child's registered pendings; `_forward`'s send path does not also emit; the only direct `_forward` completions are a pre-registration spawn/resolution failure and the R3-C dead-window case (neither of which has a pending or a competing death completion) — so exactly one response reaches the downstream per request.
- **Structural verbatim + single `str` serialization boundary (R-11)** — "verbatim" means STRUCTURAL JSON equality modulo the rewritten top-level id (the object-envelope design supports exactly this); `conn.outbound`/the transport outbound queue are typed `str`, serialized once at the routing/enqueue point; opacity tests assert deep-equality, not byte-identity.
- **`RELAY_SESSION_SOURCE = "panels-relay"`** — a distinct `source` so relay-owned sessions are self-labeled and provably not role-child sessions; a source tag is the only in-store ownership marker.
- **`CHILD_CLEANUP_BUDGET_SECONDS` (= `SHUTDOWN_GRACE_DEFAULT`) for stale/partial cleanup (R-12)** — the named operational budget for the in-line bounded teardown of a stale or partial child during a respawn/failed-spawn, replacing the undefined `SHORT`; the pool-wide `shutdown` uses the app's single shared deadline, this constant governs only the in-spawn cleanup that has no ambient app deadline.
- **`INIT_EXECUTOR_MAX_WORKERS` (= 8) bound on the pool's init executor (R3-G)** — a small named bound so a concurrent-spawn burst is capped and cannot occupy every default-executor worker; the only tuning knob, deliberately modest for an off-by-default S1 foundation.
- **Subscribe is routing-only (does not spawn)** — the contract makes spawn demand-driven; subscribe only primes routing, and spawn is triggered by the first forwarded request addressing the employee.
- **No `HERMES_TUI_SKILLS` set by the relay pool, and it is stripped from inherited env** — role-skill selection is out of S1 scope, and stripping it (with `PLAN_TICKET_ID`) from `base_env` prevents a stale inherited identity leaking into a child.
- **Composition helper `compose_relay_backend_if_enabled` (sixth file, counted — R-12)** — extracting the exact `_lifespan` composition into a testable helper lets the gate test prove the flag is honored at `test_mode=False` by driving the real composition path; it is the sole import site for `EmployeeChildPool`/`EmployeeChildRelay`, so `server.py` imports neither directly.
- **No timeout on the stdout read** — the transport's blocking `read_stdout()` returns only a line or `None` (EOF), so there is no "timeout-is-not-death" hazard; death is EOF or a failed write, nothing else.
- **Removed unearned/contradictory artifacts (R-12, R3-F)** — the file inventory is consistent at six implementation files (incl. `composition.py`) and SEVEN test files (13 substantive new files + the `__init__.py` marker = 14); `EmployeeChildRelay.request_timeout` is dropped (unused); the undefined `SHORT` is replaced by `CHILD_CLEANUP_BUDGET_SECONDS`; `server.py` no longer imports `EmployeeChildPool`/`EmployeeChildRelay` directly. The previously-removed `live_session_id`, `available()`, and `employee_bucket_marker` remain gone.

## S1 limitations (explicitly out of scope, per D-s1-concurrency-scope)

Each edge below is a conscious cut for an off-by-default S1 foundation, not an oversight, and each is
**trigger-bound**: re-examine at **S2, when the backend gains real browser consumers** — not before.
`D-s1-concurrency-scope` rules them documented-not-built, because the contract's child-death acceptance
is "mid-traffic exit → child-reset + respawn" (contract:115-116), not lossless delivery under every
write/EOF interleaving, and because building every surfaced edge would expand S1 past its contract
(everything-earns-its-existence). The ONE deep-edge item built in this revision is the dedicated bounded
init/shutdown executor (R3-G); the two below are named, deferred, and bound to S2.

- **Final-frame-vs-write-death ordering.** A failed-write death is signaled from the OUTBOUND WRITER thread (via `_mark_dead` → `deliver_child_death`), while stdout frames are sequenced from the SEPARATE stdout reader thread. Both schedule onto the loop independently, so a final already-emitted stdout frame could be dropped if the write-side death retires the `ChildBinding` (in `deliver_child_death`) before that last stdout frame is read and delivered. **Re-examine at S2, when the backend gains real browser consumers.** Rationale: death semantics are child-reset + respawn, and the downstream re-syncs from durable session state on the next request, so lossless frame ordering *across* a death is not a contract promise. The eventual mitigation (an S2 concern) is a single per-child ingress sequencer that drains all final stdout frames before emitting death, plus a final-frame-versus-failed-write barrier test.
- **Unbounded queues / overload policy.** The per-child outbound `queue.Queue` and each per-downstream `asyncio.Queue` `outbound` are UNBOUNDED; a wedged child pipe or a stuck downstream socket that never drains could grow memory (and the pending maps alongside it), because a blocked send does not stop admission. **Re-examine at S2, when the backend gains real browser consumers.** Rationale: in S1 the only consumers are tests, so no queue is ever driven unbounded; a slow *real* downstream is what changes the calculus, and that arrives with S2. The eventual mitigation (an S2 concern) is bounded queues with a defined overload/backpressure policy (drop-oldest, disconnect-slow-consumer, or an admission limit that completes over-limit forwards with an overload error), plus overload-path tests.

These two edges are the full set of trigger-bound deferred limitations for S1. The writer-vs-`close_stdin` shutdown race is NOT a separate limitation: it is already subsumed by the design — the outbound writer thread is the SOLE owner and closer of stdin (it closes stdin itself on the `_SHUTDOWN_SENTINEL`), so `transport.shutdown` never calls `close_stdin` from another thread, and a mid-`send` blocked write on a wedged pipe is broken by the bounded `kill()` (noted in §1's `transport.shutdown`), not left racing. Nothing else in the shutdown/teardown path is left unbounded: every wait/join is `remaining()`-bounded against the one deadline (with the leader/follower earliest-deadline discipline, R3-round3-2), and the dedicated executors (R3-G) remove the default-executor starvation path entirely.
