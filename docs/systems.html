Read By Question

Start with the system that owns the question. Then open the details only where the answer needs code paths or boundary notes.

  • What is true? Record System. SQLite records are truth; a commit tells screens to refetch.
  • Who can decide? Ticket Gate System. Workers propose; the proposal resolver and human approvals settle.
  • Why did work run? Worker Orchestration. The readiness loop decides a Ticket is ready, claims it with one status flip, and sends the step.
  • Where is conversation? ACP typed replay and live updates share one durable Employee session.
  • Why did UI update? Human UI System. A change signal restages every cached read; only what is on screen refetches.

The Systems

Each row names one system, what it owns, and where the code lives.

01 The Record SystemCanonical objects and the change signal.

SQLite stores sprints, sprint items, tickets, days, ideas, and links. The intended shape is contracts for records and enums, writer modules for mutations, API files for HTTP, and logic files for pure rules.

A write should go through a canonical writer and let the UI refetch from the server. Committing a write announces itself — the announcement carries no entity, kind, or payload — and both the browser and the readiness loop answer by asking the record again.

Code paths: src/planner/core/db.py, src/planner/core/change_signal.py, src/planner/*/contracts.py, src/planner/*/data.py

02 The Planning ObjectsSprints, items, tickets, days, ideas, and links.

Sprints are two-week pushes. Sprint items are larger chunks inside or outside a sprint. Tickets are worker-sized work units. Days are daily overview records and ordered ticket lists. Ideas are loose thoughts that are not work yet.

The Board is today's execution board, not an all-ticket inventory. The readiness loop starts from that same membership-only candidate set, then asks the complete readiness decision about each Ticket.

Code paths: src/planner/sprints/, src/planner/tickets/, src/planner/days/, src/planner/core/links.py

03 The Ticket Gate SystemThe correctness center.

A Ticket stores stage for its work Stage. Its Worker type declares the available Stages; coding uses kickoff, success, approach, plan, implementation, closeout, done, or dropped. ticket_status is separate runtime control — one word for what is happening on the Ticket right now. There are eight: empty (at rest and ready), blocked (at rest, waiting on a live blocker), agent (a worker is running a step), paired (working together), awaiting_approval (a proposal is waiting for the human), needs_user (the worker asked for help), user (the user has taken the stage), and errored (a confirmed backend Worker failure).

blocked stands in for empty and nothing else. A Ticket that comes to rest with nothing running lands there while a live blocker remains, and only empty Tickets are ever started automatically. The write that removes the cause — finishing, dropping, or deleting the blocking Ticket, or removing the link — deletes the links it held and rewrites each blocked Ticket back to empty in the same transaction, or leaves it blocked when another live blocker remains.

Workers write proposals to the six fields: kickoff, success, approach, plan, implementation, and closeout. The proposal resolver is the only code that can settle a proposal or advance stage. Scope is ceiling plus at_cap; it decides how far a worker may go before the human must approve again. The UI labels the parked-proposal cap choice Continue while the stored value remains propose.

Stage ownership decides who drives the current Stage: worker, user, or paired. Worker-owned Stages can be started automatically, user-owned Stages rest at user, and paired Stages get one automatic opening turn and then rest at paired, where human conversation continues in the same Ticket conversation and no further step is started automatically. Any real paired proposal parks for approval. The Worker type selects a default backend key. During pristine Kickoff, the Ticket may instead select hermes, codex, or claude. A session, binding, or move beyond Kickoff freezes that stored choice.

Code paths: src/planner/tickets/contracts.py, src/planner/tickets/logic/machine.py, src/planner/tickets/logic/resolution.py, src/planner/tickets/data.py

04 Worker OrchestrationDecide a Ticket is ready, claim it, send the step.

One complete decision owns worker-step readiness. It returns yes only when the Ticket is on the planning day, its current Stage is not terminal and has a gated field, the user does not own that Stage, its ticket_status is empty, no proposal is already parked, scope permits the next proposal, and its Closeout lane is free. The empty check is what keeps blocked, paired, errored, user-held, help-waiting, approval-waiting, and already-out Tickets from starting; the decision reads only current facts.

One more question the record cannot answer is asked before anything is sent: whether that Ticket's worker is already busy. That is the conversation system's fact, and a busy worker is left alone for the pass.

Taking the Ticket out of empty under BEGIN IMMEDIATE is the claim — to agent for a worker-owned Stage, paired for a paired one. The readiness decision runs again inside that write, so two racers both re-check under the same lock and only one writes. There is no claim stamp and no run record.

The step is then sent as a real message: the opening instruction plus any pending worker context, whose receipts are ticked off only after the send reported started or queued. Both count as delivered. Only a refusal gives the claim back, guarded on the status and the moment it was written so a late release cannot erase a later legitimate move.

Nothing watches the turn end. A Ticket moves again only when someone acts on it, and a crash leaves a Ticket whose status and whose live worker disagree — visible on purpose, with no recovery sweep to pretend otherwise.

The loop subscribes to the change signal, so any committed write in the server process makes it check again at once. The signal carries no Ticket id, owns no state, and sends no IPC; a failed delivery is logged and ignored, because SQLite and the periodic timer remain canonical. Over-waking is deliberate and cheap: the re-check is read-only and complete.

Code paths: src/planner/runtime/worker_step_readiness.py, src/planner/runtime/worker_step_readiness_loop.py, src/planner/runtime/conversation_start.py, src/planner/core/change_signal.py, src/planner/core/loops.py

05 The Conversation SystemThe one way Panels talks to an AI agent.

One conversation is one agent process — hermes, codex, or claude — working in a folder, plus a permanent notebook of everything that happened in it. Every screen that shows a conversation uses it, and so does worker orchestration. There is no second path and no stand-in.

The rest of Panels can do exactly five things to a conversation: start it, send text into it, interrupt its running turn, kill its activity outright, and ask whether it is running — plus one more question, whether a permission ask is waiting. Nothing else crosses the boundary.

A conversation is named by an id its caller owns. A Ticket keeps its own in tickets.conversation_id and the Chief keeps its own in the agents table. The backend process’s own session id is internal and rebindable, and appears nowhere outside the system.

Sending says what actually happened to that text and never more: it started a turn, it is held until the agent is free, it was injected into a running turn, or it was refused for a named impossibility. A busy agent is never a refusal — a message the system can hold is held. Steering is a per-backend fact rather than a negotiation: hermes can take text into a running turn and the other two cannot.

Which backends exist is a closed set of exactly hermes, codex and claude, and one door turns untrusted text into a member of it. What each one is on this machine — installed, which version, signed in as whom, which models and which reasoning efforts each model takes — is one answer, probed when asked and kept until asked again.

Code paths: src/planner/conversation/contracts.py, src/planner/conversation/system.py, src/planner/conversation/storage.py, src/planner/conversation/snapshot.py, src/planner/conversation/backends/

06 The Browser ConversationA pane over the record, read the way every other screen reads.

A pane reads the rows of its conversation after the position it already holds, then keeps up over a live tail of the same rows. Opening, reloading and opening a second tab are the same act. Nothing holds a socket open to Panels.

It renders human and agent messages, collapsed thought and tool detail, plans, diffs, permissions, delivery fates, and one persistent status line. The composer offers Steer where the backend supports it, Send Now, run-when-free, Stop, and New.

Durable Ticket artifact previews and generic file previews remain available through their normal file routes.

Code paths: src/planner/conversation/api.py, web/src/components/conversation/, web/src/lib/conversation/

07 The Human UI SystemSvelte resource projections.

One catalogue names every cached server read and the address it comes from: board, review, day:today, sprint:current, one Ticket by id, and the rest. Screens ask for a read by name; the shared cache serves one request to all of them.

Review walks one oldest-first list of today’s Tickets whose ticket_status is awaiting_approval or needs_user, plus the global running-worker count.

The server holds open a change stream at GET /api/changes and sends one contentless line per committed write. The browser marks every cached read stale; only the reads a screen is currently showing are fetched again, and a burst of writes collapses into one round. A refetch that comes back identical leaves the page alone, so typing, focus, and scroll survive. A successful UI write does the same thing itself without waiting for the stream. There is no whole-screen reload or canonical client store; the server remains the source of truth.

The stream also owns the connection pill: Connected while it is open, Reconnecting while the browser retries. Opening the stream refetches what is on screen, which is how a gap is repaired.

ACP conversation state does not enter that cache. Its transport, controller, and reducer own one typed socket projection keyed by Employee, session, generation, and sequence. Canonical Ticket, Board, Sprint, and Review reads stay server-owned REST resources.

Managed Markdown has one browser-DOM owner. managedMarkdown.ts renders through the hardened renderer, mounts file previews, maintains editable atomic blocks, serializes edits, reconciles moved or deleted previews, and tears everything down. MarkdownBlock and InlineEdit only supply product values and coordinate read-only presentation or ordinary editing and save behavior. Plain contenteditable helpers remain separate from Markdown lifecycle work.

Code paths: web/src/App.svelte, web/src/routes/, web/src/lib/queryCatalogue.ts, web/src/lib/queryClient.ts, web/src/lib/changeStream.ts, web/src/lib/mutate.ts, web/src/lib/conversation/, web/src/components/conversation/, web/src/lib/managedMarkdown.ts, web/src/lib/editableText.ts

08 The CLI And Authority SystemOrdinary, worker, and Chief actions.

panels speaks HTTP to the server. Its command groups include project, day, ticket, sprint, worker, and chief. Ordinary commands preserve an ambient actor or send none; production worker and Chief gateways set their roles explicitly. Chief external-work intake is exceptional and is not a generic Stage setter.

A missing X-Plan-Actor means unattributed, not human. chief is explicit; every other non-empty actor is an attributed non-Chief agent. Direct-only routes allow unattributed and Chief requests while rejecting worker agents.

Code paths: src/planner/cli/main.py, src/planner/cli/http.py, src/planner/core/authctx.py

Boundaries That Matter

The repo is understandable because the number of truth-changing doors is small.

  • Proposal resolver Owns Ticket field values and Ticket stage transitions.
  • Runtime writers Own ticket_status, the durable state of control.
  • Canonical writers Own record mutation. Most live in domain data.py files.
  • ACP conversation composition Owns durable bindings, typed replay, active turns, permissions, and backend children.
  • Frontend Owns rendering and local drafts only. Within it, managedMarkdown.ts alone owns rendered Markdown DOM and preview lifetime.
  • CLI Is an action surface, not a decision surface.

System-Level Friction

These are boundary problems, not local style problems.

01 A conversation id is owned by whoever names it.One column, no mirror.

A Ticket keeps the id of its conversation in tickets.conversation_id, and the Chief keeps its own in the agents table. There is no separate table owning it and nothing to keep in step: the id is a column on the row it belongs to. The backend process’s own session id is internal to the conversation system and is rebound without anything outside it noticing.

02 Sprint item status is a read projection.Items derive progress from child tickets and blocking links.

Sprint items no longer store their own status. They derive todo, in_progress, blocked, or done from child tickets and open links.kind='blocks' rows.

03 The frontend reads the Worker type manifest.The server owns Stage order and gates.

GET /api/worker-types supplies each Worker type's Stage order, gating fields, and advance targets. The frontend renders that served metadata instead of copying the Ticket Stage machine.

Deferred

  • Failed-run recovery An errored ticket has no retry or clear path.
  • Automatic rollover Days materialize, but no worker drafts the next day's overview.
  • Idea conversion Ideas stay ideas until promotion or archive exists.
