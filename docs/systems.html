Read By Question

Start with the system that owns the question. Then open the details only where the answer needs code paths or boundary notes.

  • What is true? Record System. SQLite records are truth; events tell screens to refetch.
  • Who can decide? Ticket Gate System. Workers propose; the resolution engine and human approvals settle.
  • Why did work run? Employee Runtime. AutomaticEmployeeStepDiscoveryLoop checks Automatic Employee-step eligibility; EmployeeStepRunner runs one worker step.
  • Where is chat? Hermes Gateway and Chat. The planner stores session keys, not transcripts.
  • Why did UI update? Human UI System. Events map to resource keys and cause targeted refetches.

The Systems

Each row names one system, what it owns, and where the code lives.

01 The Record SystemCanonical objects and event doorbells.

SQLite stores sprints, sprint items, tickets, days, ideas, links, and events. The intended shape is contracts for records and enums, writer modules for mutations, API files for HTTP, and logic files for pure rules.

A write should go through a canonical writer, append an event, and let the UI refetch from the server. Events are append-only. Records are not.

Code paths: src/planner/core/db.py, src/planner/core/events.py, src/planner/*/contracts.py, src/planner/*/data.py

02 The Planning ObjectsSprints, items, tickets, days, ideas, and links.

Sprints are two-week pushes. Sprint items are larger chunks inside or outside a sprint. Tickets are worker-sized work units. Days are daily overview records and ordered ticket lists. Ideas are loose thoughts that are not work yet.

The Board is today's execution board, not an all-ticket inventory. AutomaticEmployeeStepDiscoveryLoop starts with that same membership-only candidate set, then asks the complete Automatic Employee-step eligibility decision about each Ticket.

Code paths: src/planner/sprints/, src/planner/tickets/, src/planner/days/, src/planner/core/links.py

03 The Ticket Gate SystemThe correctness center.

A Ticket stores stage for its work Stage. Its Worker type declares the available Stages; coding uses kickoff, success, approach, plan, implementation, closeout, done, or dropped. ticket_status is separate runtime control: empty, running, awaiting approval, user takeover, or errored.

Workers write proposals to the six fields: kickoff, success, approach, plan, implementation, and closeout. The resolution engine is the only code that can settle a proposal or advance stage. Scope is ceiling plus at_cap; it decides how far a worker may go before the human must approve again.

Code paths: src/planner/tickets/contracts.py, src/planner/tickets/logic/machine.py, src/planner/tickets/logic/resolution.py, src/planner/tickets/data.py

04 The Employee RuntimeAdvisory automatic eligibility discovery and separate step execution.

One complete decision owns Automatic Employee-step eligibility. It returns yes only when all seven facts hold:

  1. The Ticket belongs to the supplied planning_day_id — today's day during automatic discovery.
  2. Its ticket_status is empty.
  3. Its Stage is not terminal.
  4. Its Stage has a next gated field.
  5. That field has no parked proposal.
  6. Its ceiling and at_cap allow another proposal; the Ticket is not at or beyond a stopping ceiling.
  7. It has no active blocker.

AutomaticEmployeeStepDiscoveryLoop is read-only and advisory. It selects only Tickets that belong to today's day, then calls the complete decision for each membership candidate. It does not claim Tickets, write state, or contact Hermes.

EmployeeStepRunner separately owns one worker step. Its final claim starts BEGIN IMMEDIATE, reloads the Ticket and its Worker type definition, resolves the planning day inside the transaction, and calls the same complete decision. A stale discovery result cannot change status, create chat state, call the gateway, or build a prompt. After a successful claim, the runner marks the Ticket running, resumes or creates its Hermes session, submits one prompt, and settles runtime status when the turn ends.

A direct requested revision bypasses Automatic Employee-step eligibility and planning-day resolution, uses a reserved runner handoff, and strictly resumes the Ticket's stored Hermes session.

Ticket, Day membership, and blocking-link actions commit first, then call AutomaticEmployeeStepEligibilityWake.wake(). Runner settlement does the same. This best-effort same-process wake carries no Ticket id, owns no state, and sends no IPC. Failure is logged and ignored; SQLite and the periodic discovery timer remain canonical. The polling-lock owner uses LoopAutomaticEmployeeStepEligibilityWake; processes without the lock receive NoOpAutomaticEmployeeStepEligibilityWake.

Code paths: src/planner/runtime/automatic_employee_step_eligibility.py, src/planner/runtime/automatic_employee_step_discovery_loop.py, src/planner/runtime/automatic_employee_step_eligibility_wake.py, src/planner/runtime/employee_step_runner.py, src/planner/tickets/actions.py, src/planner/days/actions.py, src/planner/core/link_actions.py, src/planner/core/loops.py

05 The Hermes Gateway SystemThe outside worker process boundary.

Hermes is outside the planner. Production startup installs a shared gateway owner on app state. That owner spawns the gateway child lazily on first use. Tests use fake adapters and never call the real gateway.

Tickets and days store only a chat_session_key. Hermes owns the transcript. When the planner needs history, it resumes the session lazily and normalizes returned messages.

Code paths: src/planner/core/adapters/, src/planner/minds/shared_gateway.py, src/planner/minds/gateway.py, src/planner/minds/config.py

06 The Chat SystemHuman conversation on the same durable ticket session.

Ticket chat and automatic worker steps use the same durable ticket session. EmployeeStepRunner stores a new or resumed session key before submitting the worker prompt, so worker tools can resolve their ticket during the turn.

Human chat sends are rejected while ticket_status=agent_running_step. History stays readable. There is no queue behind the active worker step.

Code paths: src/planner/chat/, web/src/components/ChatPanel.svelte

07 The Human UI SystemSvelte resource projections.

The browser does not keep a canonical client store. Screens subscribe to resources such as ticket:<id>, board, review, day:today, and sprint:current.

Review contains only today’s parked Ticket proposals and the global running-worker count.

WebSocket event batches map to resource keys. The browser refetches only those keys from the server.

Code paths: web/src/App.svelte, web/src/routes/, web/src/lib/resources.svelte.ts, web/src/lib/ws.ts, web/src/lib/eventMapping.mjs

08 The CLI And Authority SystemOrdinary, worker, and Chief actions.

panels speaks HTTP to the server. Its command groups include project, day, ticket, sprint, worker, and chief. Ordinary commands preserve an ambient actor or send none; production worker and Chief gateways set their roles explicitly. Chief external-work intake is exceptional and is not a generic Stage setter.

A missing X-Plan-Actor means unattributed, not human. chief is explicit; every other non-empty actor is an attributed non-Chief agent. Direct-only routes allow unattributed and Chief requests while rejecting worker agents.

Code paths: src/planner/cli/main.py, src/planner/cli/http.py, src/planner/core/authctx.py

Boundaries That Matter

The repo is understandable because the number of truth-changing doors is small.

  • Resolution engine Owns Ticket field values and Ticket stage transitions.
  • Runtime writers Own ticket_status, the durable state of control.
  • Canonical writers Own record mutation and event emission. Most live in domain data.py files.
  • Hermes Owns chat transcripts. The planner stores session keys.
  • Frontend Owns rendering and local drafts only.
  • CLI Is an action surface, not a decision surface.

System-Level Friction

These are boundary problems, not local style problems.

01 Chat session-key ownership is a special writer exception.Most mutations now live behind domain writers.

Chat session-key writes live in src/planner/chat/service.py because they coordinate with the gateway during live conversation setup. The usual rule still holds elsewhere: domain mutations go through canonical writer functions.

02 Sprint item status is a read projection.Items derive progress from child tickets and blocking links.

Sprint items no longer store their own status. They derive todo, in_progress, blocked, or done from child tickets and open links.kind='blocks' rows.

03 The frontend reads the Worker type manifest.The server owns Stage order and gates.

GET /api/worker-types supplies each Worker type's Stage order, gating fields, and advance targets. The frontend renders that served metadata instead of copying the Ticket Stage machine.

04 Gateway bootstrap is indirect.The registry shape does not show the production owner directly.

The adapter registry returns a real adapter placeholder. Production startup replaces app-state adapters with SharedGateway. This keeps tests clean, but it is not obvious from the registry.

Deferred

  • Failed-run recovery An errored ticket has no retry or clear path.
  • Automatic rollover Days materialize, but no worker drafts the next day's overview.
  • Chat queue Human sends are rejected while a ticket worker is active.
  • Idea conversion Ideas stay ideas until promotion or archive exists.
