Read By Question

Start with the system that owns the question. Then open the details only where the answer needs code paths or boundary notes.

  • What is true? Record System. SQLite records are truth; a commit tells screens to refetch.
  • Who can decide? Ticket Gate System. Workers propose; the resolution engine and human approvals settle.
  • Why did work run? Employee Runtime. AutomaticEmployeeStepDiscoveryLoop checks Automatic Employee-step eligibility; EmployeeStepRunner runs one worker step.
  • Where is conversation? ACP typed replay and live updates share one durable Employee session.
  • Why did UI update? Human UI System. A change signal restages every cached read; only what is on screen refetches.

The Systems

Each row names one system, what it owns, and where the code lives.

01 The Record SystemCanonical objects and the change signal.

SQLite stores sprints, sprint items, tickets, days, ideas, and links. The intended shape is contracts for records and enums, writer modules for mutations, API files for HTTP, and logic files for pure rules.

A write should go through a canonical writer and let the UI refetch from the server. Committing a write announces itself — the announcement carries no entity, kind, or payload — and both the browser and the discovery loop answer by asking the record again.

Code paths: src/planner/core/db.py, src/planner/core/change_signal.py, src/planner/*/contracts.py, src/planner/*/data.py

02 The Planning ObjectsSprints, items, tickets, days, ideas, and links.

Sprints are two-week pushes. Sprint items are larger chunks inside or outside a sprint. Tickets are worker-sized work units. Days are daily overview records and ordered ticket lists. Ideas are loose thoughts that are not work yet.

The Board is today's execution board, not an all-ticket inventory. AutomaticEmployeeStepDiscoveryLoop starts with that same membership-only candidate set, then asks the complete Automatic Employee-step eligibility decision about each Ticket.

Code paths: src/planner/sprints/, src/planner/tickets/, src/planner/days/, src/planner/core/links.py

03 The Ticket Gate SystemThe correctness center.

A Ticket stores stage for its work Stage. Its Worker type declares the available Stages; coding uses kickoff, success, approach, plan, implementation, closeout, done, or dropped. ticket_status is separate runtime control — one word for what is happening on the Ticket right now. There are eight: empty (at rest and ready), blocked (at rest, waiting on a live blocker), agent (a worker is running a step), paired (working together), awaiting_approval (a proposal is waiting for the human), needs_user (the worker asked for help), user (the user has taken the stage), and errored (a confirmed backend Worker failure).

blocked stands in for empty and nothing else. A Ticket that comes to rest with nothing running lands there while a live blocker remains, and only empty Tickets are ever started automatically. The write that removes the cause — finishing, dropping, or deleting the blocking Ticket, or removing the link — deletes the links it held and rewrites each blocked Ticket back to empty in the same transaction, or leaves it blocked when another live blocker remains.

Workers write proposals to the six fields: kickoff, success, approach, plan, implementation, and closeout. The resolution engine is the only code that can settle a proposal or advance stage. Scope is ceiling plus at_cap; it decides how far a worker may go before the human must approve again. The UI labels the parked-proposal cap choice Continue while the stored value remains propose.

Stage ownership decides who drives the current Stage: worker, user, or paired. Worker-owned Stages can be discovered automatically, user-owned Stages rest at user, and paired Stages get one automatic opening turn and then rest at paired, where human conversation continues the same Employee session and no further step is started automatically. Any real paired proposal parks for approval. The Worker type selects a default backend key. During pristine Kickoff, the Ticket may instead select hermes, codex, or claude. A session, binding, or move beyond Kickoff freezes that stored choice.

Code paths: src/planner/tickets/contracts.py, src/planner/tickets/logic/machine.py, src/planner/tickets/logic/resolution.py, src/planner/tickets/data.py

04 The Employee RuntimeAdvisory automatic eligibility discovery and separate step execution.

One complete decision owns Automatic Employee-step eligibility. It returns yes only when the Ticket is on the planning day, its current Stage is not terminal and has a gated field, the user does not own that Stage, its ticket_status is empty, no proposal is already parked, scope permits the next proposal, and no Employee step is already running. The empty check is what keeps blocked, paired, errored, user-held, help-waiting, and approval-waiting Tickets from starting; the decision reads only current facts.

AutomaticEmployeeStepDiscoveryLoop is read-only and advisory. It selects only Tickets that belong to today's day, then calls the complete decision for each membership candidate. It does not claim Tickets, write state, or contact the ACP backend.

EmployeeStepRunner separately owns one worker step. Its final claim starts BEGIN IMMEDIATE, reloads the Ticket and its Worker type definition, resolves the planning day inside the transaction, and calls the same complete decision. A stale discovery result cannot change status, create a run, call the gateway, or build a prompt. After a successful claim, the runner creates one running employee_step_runs row and sends the step through AcpStepGateway.

employee_step_runs is correctness state only: identity, status, exact Employee session, error, and timestamps. It stores no prompt, reply, transcript, activity, usage, image, tool, or browser state. One partial index permits at most one running step per Ticket.

The gateway prepares pending worker context into the actual model prompt before ACP delivery. It acknowledges exact context revisions only after ACP admits the prompt. A correctness row is never model context.

The discovery loop subscribes to the change signal, so any committed write in the server process makes it check again at once. The signal carries no Ticket id, owns no state, and sends no IPC; a failed delivery is logged and ignored, because SQLite and the periodic discovery timer remain canonical. Over-waking is deliberate and cheap: the re-check is read-only and complete.

Code paths: src/planner/runtime/automatic_employee_step_eligibility.py, src/planner/runtime/automatic_employee_step_discovery_loop.py, src/planner/core/change_signal.py, src/planner/runtime/employee_step_runner.py, src/planner/runtime/acp_step_gateway.py, src/planner/runtime/employee_step_repository.py, src/planner/core/loops.py

05 The ACP Conversation SystemOne durable session for human and Automatic Employee prompts.

ConversationComposition owns the Employee registry, typed publication hub, turn broker, permission broker, durable binding repository, and the Automatic Employee step gateway. The server is the ACP client and uses the official ACP client library; an agent backend runs as a child process over ACP standard input and output.

conversation_session_bindings is the durable owner of ACP session identity. A Ticket mirrors that id in tickets.employee_session_id; the Chief has no second mirror. Human prompts, Automatic Employee steps, and revision guidance all reach the same binding and resume it after restart.

The turn broker owns active work, Steer, Send Now, Queue, Stop, and compaction. Permissions belong to the exact attached browser and exact session generation. Typed replay and live publication retain messages, thoughts, tools, plans, terminals, permissions, receipts, and lifecycle state without flattening them into a second transcript vocabulary.

Compaction is deliberately small in Panels: the transcript shows that it started and then whether it completed or failed with the exact reason. These boundaries contain no context. Panels waits up to 300 seconds to observe the terminal result and never reads or renders compacted context or a summary. Later replay shows the same typed boundary.

The production catalog contains exactly hermes, codex, and claude; Gemini is not registered. Hermes supports native Steer. Codex and Claude Code do not, so their active turns use Queue or Send Now. Claude Code runs one initialize-only startup preflight and closes that temporary child without creating a session. Codex starts lazily on first demand.

Code paths: src/planner/conversation/composition.py, src/planner/conversation/hub.py, src/planner/conversation/turn_broker.py, src/planner/conversation/permission_broker.py, src/planner/conversation/backend_catalog.py, src/planner/conversation/hermes_backend.py, src/planner/conversation/codex_backend.py, src/planner/conversation/claude_backend.py

06 The ACP Browser ConversationA typed pane over the server-owned conversation.

The browser uses one typed WebSocket at /api/conversation. Attach, load, and live updates share the same Employee, ACP session, binding generation, and sequence. A gap or identity mismatch fails closed and a later contiguous ready epoch recovers the pane.

The ACP pane renders human and agent messages, collapsed thought and tool detail, plans, diffs, terminal state, permissions, receipts, and one persistent status line. The composer offers Steer when supported, Send Now, Queue, Stop, ACP-advertised commands, and ordered inline images.

Conversation images are ACP content blocks, not files in a separate chat upload system. Generic file previews and durable Ticket artifact previews remain available through their normal file routes.

Code paths: src/planner/conversation/api.py, web/src/components/AcpConversation.svelte, web/src/components/acp/, web/src/lib/acp/

07 The Human UI SystemSvelte resource projections.

One catalogue names every cached server read and the address it comes from: board, review, day:today, sprint:current, one Ticket by id, and the rest. Screens ask for a read by name; the shared cache serves one request to all of them.

Review contains exactly today’s Tickets whose ticket_status is awaiting_approval, plus the global running-worker count.

The server holds open a change stream at GET /api/changes and sends one contentless line per committed write. The browser marks every cached read stale; only the reads a screen is currently showing are fetched again, and a burst of writes collapses into one round. A refetch that comes back identical leaves the page alone, so typing, focus, and scroll survive. A successful UI write does the same thing itself without waiting for the stream. There is no whole-screen reload or canonical client store; the server remains the source of truth.

The stream also owns the connection pill: Connected while it is open, Reconnecting while the browser retries. Opening the stream refetches what is on screen, which is how a gap is repaired.

ACP conversation state does not enter that cache. Its transport, controller, and reducer own one typed socket projection keyed by Employee, session, generation, and sequence. Canonical Ticket, Board, Sprint, and Review reads stay server-owned REST resources.

Managed Markdown has one browser-DOM owner. managedMarkdown.ts renders through the hardened renderer, mounts file previews, maintains editable atomic blocks, serializes edits, reconciles moved or deleted previews, and tears everything down. MarkdownBlock and InlineEdit only supply product values and coordinate read-only presentation or ordinary editing and save behavior. Plain contenteditable helpers remain separate from Markdown lifecycle work.

Code paths: web/src/App.svelte, web/src/routes/, web/src/lib/queryCatalogue.ts, web/src/lib/queryClient.ts, web/src/lib/changeStream.ts, web/src/lib/mutate.ts, web/src/lib/acp/, web/src/components/acp/, web/src/lib/managedMarkdown.ts, web/src/lib/editableText.ts

08 The CLI And Authority SystemOrdinary, worker, and Chief actions.

panels speaks HTTP to the server. Its command groups include project, day, ticket, sprint, worker, and chief. Ordinary commands preserve an ambient actor or send none; production worker and Chief gateways set their roles explicitly. Chief external-work intake is exceptional and is not a generic Stage setter.

A missing X-Plan-Actor means unattributed, not human. chief is explicit; every other non-empty actor is an attributed non-Chief agent. Direct-only routes allow unattributed and Chief requests while rejecting worker agents.

Code paths: src/planner/cli/main.py, src/planner/cli/http.py, src/planner/core/authctx.py

Boundaries That Matter

The repo is understandable because the number of truth-changing doors is small.

  • Resolution engine Owns Ticket field values and Ticket stage transitions.
  • Runtime writers Own ticket_status, the durable state of control.
  • Canonical writers Own record mutation. Most live in domain data.py files.
  • ACP conversation composition Owns durable bindings, typed replay, active turns, permissions, and backend children.
  • Frontend Owns rendering and local drafts only. Within it, managedMarkdown.ts alone owns rendered Markdown DOM and preview lifetime.
  • CLI Is an action surface, not a decision surface.

System-Level Friction

These are boundary problems, not local style problems.

01 Employee-session ownership is explicit.One binding owner; one Ticket mirror.

conversation_session_bindings owns the ACP session and binding generation. A Ticket mirrors the session id atomically; the Chief has no second mirror. Compare-and-swap replacement prevents two Employees from claiming one ACP session.

02 Sprint item status is a read projection.Items derive progress from child tickets and blocking links.

Sprint items no longer store their own status. They derive todo, in_progress, blocked, or done from child tickets and open links.kind='blocks' rows.

03 The frontend reads the Worker type manifest.The server owns Stage order and gates.

GET /api/worker-types supplies each Worker type's Stage order, gating fields, and advance targets. The frontend renders that served metadata instead of copying the Ticket Stage machine.

Deferred

  • Failed-run recovery An errored ticket has no retry or clear path.
  • Automatic rollover Days materialize, but no worker drafts the next day's overview.
  • Idea conversion Ideas stay ideas until promotion or archive exists.
