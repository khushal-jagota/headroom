Systems map

One planning record, narrow authority paths, one Worker starter, and one conversation system.

human browser ───────────────┐ direct CLI ──────────────────┼──► domain writers ─────────────► SQLite │ │ Ticket Worker ─► proposal resolver │ commit planning Worker ─► guarded Day or Sprint writer ▼ direct user ─────► user-owned Ticket gate change signal │ ┌──────────────────────────────────────────┤ ▼ ▼ mounted browser reads Worker readiness │ ▼ Ticket conversation

The proposal resolver owns gated Ticket values and Stage advances. Ordinary direct actions, guarded planning writes, and Chief intake use separate writers.

The systems

01Record and change signalCanonical state and a payload-free wake.

SQLite stores product, runtime, conversation, notification, schedule, and operational records. Domain writers commit transactions. Each commit announces that something changed. Mounted browser reads and Worker readiness then ask the record again. A commit stays quiet only where no screen is waiting for its rows: managed skill history, and the conversation rows an open conversation is the only reader of, which is handed them directly.

02Planning domainsDays, Sprints, Sprint Items, Tickets, Ideas, and Projects.

Each domain owns its contracts, rules, writers, views, and routes. Tickets own their Project and optional Sprint placement. Outcomes hold shared context across Sprints. Commitments select them before Tickets exist. Carry-forward moves only explicitly selected unfinished Tickets; completed history stays put. The Sprint view keeps uncommitted work visible. The planning date changes at 05:00 local time.

03Tickets, gates, and Worker typesWorkflow shape, proposals, scope, ownership, and control state.

A Worker type declares Stages, gated fields, ownership, specialist skill, and launch defaults. Workers propose gated fields. The resolver settles them. Scope controls autonomous progress. Review and Workspace project the Ticket's current operating state.

src/planner/tickets/ · src/planner/worker_types/ · src/planner/worker_settings/

04Scheduled Ticket creationExact-minute Ticket supply with durable receipts.

A due occurrence creates one ordinary Ticket or records suppression or failure. The loop does not backfill downtime. Scheduling ends at Ticket creation and Day placement. The commit hands the Ticket to ordinary readiness.

src/planner/scheduled_tickets/ · scheduled-tickets.md

05Worker orchestrationDecide, claim once, and send the Stage instruction.

One read-only decision checks today's Ticket, Stage, ownership, status, proposal, scope, Closeout lane, and conversation activity. One guarded status flip is the claim. Started and queued sends succeed. Nothing watches the turn end.

src/planner/runtime/ · src/planner/worker_context/

06Conversation systemOne durable notebook and one live agent per active conversation.

Hermes, Codex, and Claude share one contract. The system sends messages, manages held work, interrupts activity, records finished events, and reports live requests for the user. Tickets, the Chief, and Worker steps all use it.

src/planner/conversation/ · web/src/components/conversation/

07Human interfaceServer projections with targeted refetch and shared conversations.

The Svelte app renders Home, Review, Workspace, Ticket, Sprint, capture, configuration, backend, notification, and schedule surfaces. The Chief lives in Workspace. Product queries refetch after contentless change signals. Conversations follow their event tail.

web/src/ · assets/ · web/dist/

08CLI and authorityDirect actions, Worker proposals, planning claims, and Chief intake.

The CLI speaks HTTP. Direct-only routes reject Worker claims. Three planning Worker types receive only their matching Day or Sprint write. A direct user can settle the unset gate of the current user-owned Stage. No operation exposes a general Stage setter.

src/planner/cli/ · src/planner/core/authctx.py

09Runtime and operationsIsolated environments, exact-app deployment, backups, and notifications.

Live runs one Git-free app with persistent data and logs. Staging and Ticket servers use isolated state. Deployment replaces only the app and restores a verified snapshot on failure. Backups and Web Push preserve durable product state.

Boundaries that matter

  • Proposal versus valueA Worker proposal is inert until the resolver accepts it.
  • Signal versus stateThe signal announces a commit. The record says what changed.
  • Status versus livenessTicket status is the last control decision. Conversation activity is current.
  • Stored versus delivered contextThe model sees context only after a prompt carries it.
  • Conversation versus backend sessionThe caller owns the conversation id. The conversation system owns the backend handle.
  • Managed versus packaged skillsdata/skills is live authority. Codex and Claude expose all managed Panels skills. Hermes uses an allowlist that currently omits the general specialist.
  • Human and agent authorityDirect actions, Worker proposals, guarded planning writes, and Chief intake use different admission paths.

Deferred

Errored Tickets have no retry path. Held messages are not restart-durable. Exact-minute schedules do not backfill downtime. The Hermes skill allowlist omits panels-worker-general.
