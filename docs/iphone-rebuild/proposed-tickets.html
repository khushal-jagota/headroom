iPhone app rebuild — proposed Tickets

Planning Ticket "Plan the Panels iPhone app rebuild from the approved mockup". Stage: Proposed Tickets. 22 November 2026.

Eight Tickets carry the approved answers. Seven run on Mac 1, one on VPS 1. All are coding Tickets in the Panels project, assigned to the Chief because no active Manager covers the iPhone app. Each Ticket gets the Brief below. Each Brief is a proposal at the Ticket's first gate, so Khushal reviews it there. The decisions behind every Ticket are in the question tree.

Shared rules in every Brief

  • Reshape the current app in ios/. Do not rebuild it fresh. Treat the existing code as a base to repair, not as proven: the read side causes the known staleness, and the offline layer is over-built in places.
  • Nothing is edited in the app. The composer is the only place to type.
  • No connection state on screen: no cover screen, banners, toasts or "Delivery uncertain". Failures show on the item itself.
  • Built-in iOS controls where appropriate. Our own controls only where needed, and then impeccable.
  • No compatibility work for old phone builds. Khushal is the only user.
  • Mac rules: build output outside artifacts (under TMPDIR). Book Simulator time through the Wren schedule Managers ("Ship Wren to the App Store", "Improve Wren"), at most two Simulators on the Mac. Never take over Khushal's screen.
  • Prove bad-connection behavior with Simulator tests. Update the file lists in ios/scripts/test-offline.sh when files move.

The Tickets

1. Give answers to agent asks a receipt, so a phone can queue themcoding · VPS 1 · no blockers
Outcome An answer to a permission ask or a worker question can carry an operation ID. The server saves a receipt with the answer, and a lookup returns it. A repeat with the same ID returns the saved receipt. The phone can tell "my answer landed" from "the ask was no longer waiting". Owns The server routes .../permission-answers and .../user-input-answers, the receipt storage and lookup, tests, and the iOS compatibility review update. Leaves elsewhere All phone code (Ticket 5). Web callers keep working unchanged. Inherited Same pattern as the decision-operations route (answer and receipt in one transaction). No support for old phone builds needed. Local questions Route shape, receipt retention, whether the web adopts the receipts now.
2. Replace the iPhone tab shell with Review as root and a slide-over Sidebar, and strip what goescoding · Mac 1 · no blockers
Outcome One NavigationStack with Review as the root. The slide-over Sidebar, built from today's Workspace list, replaces the tab bar: Chief first, active Managers, a collapsed Settled group, Review with its badge and the Settings gear at the bottom. The strip list is gone. Owns
  • AppShell.swift, Navigation.swift, the Sidebar, notification links into the new stack, foreground entry.
  • Removing: MountedTabContent and the tab bar, AgentPageBackGesture, Chief Diagnostics, Feedback, WorkspaceContextMenu.swift and every long-press menu and preview, the Steer / Queue / Send now menu.
  • Removing every edit: recap edits, renames, goal text edits, proposal text edits, Remove blocker.
  • Fixing the second conversation surface that ConversationNavigation mounts.
  • What state survives a move between Sidebar destinations.
Leaves elsewhere The Review screen itself (Ticket 6). Sheets (Ticket 4). Data and freshness (Ticket 3). The cover screen and status notes (Ticket 5). Inherited Each Sidebar destination keeps its own pages. Unsent words survive everywhere. Usage, Ideas, VPS and the Goals list stay as they are, behind the Settings gear. Goals stay on Chief and Manager pages. Chart scrubbing on goal charts stays. Chief, Manager, Ticket and Conversation pages stay close to today's app. Local questions Sidebar gesture and animation, how Review learns that Khushal visited another destination (Ticket 6 uses it).
3. Keep the iPhone app's data current on every open and every pull, without overloading the servercoding · Mac 1 · no blockers
Outcome The navigation-view stream stays the one read model and is repaired. Every app open and every pull gets fresh server data. A silent connection is noticed and replaced. Fewer full reloads reach the server. Owns AppStore.swift follow loop and refresh(), connection state, a liveness check on the server heartbeat, reload cuts (no new stream on brief inactive moments, open the new scope before closing the old one as web does, read ahead a few cards only), the saved copy at launch. Leaves elsewhere The Review screen's own held cards, the main staleness cause (Ticket 6). The foreground hook in the shell (Ticket 2 calls this Ticket's entry point). Inherited Every screen shows its saved copy at once and swaps in fresh data without any sign. The code-read diagnosis is in the planning research notes. Reproduce each cause in a test before the fix. Local questions The liveness timeout, the read-ahead count, an age limit for the saved copy.

5. Make iPhone sending quiet and dependable on a bad connectioncoding · Mac 1 · waits for 1
