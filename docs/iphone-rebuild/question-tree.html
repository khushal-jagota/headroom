1. The overall approach constrains every part

1.1 Rebuild the app fresh, or reshape the current app in place?settled
Recommended answer · Group 1, sent 22 Nov

Reshape in place. The data, offline and decision code is solid and well tested (about 7,900 lines of host tests). Keep: networking, persistence, outbox, the navigation-view client, models, ConversationModel, Ticket, Manager, Chief, Artifacts, Notifications. Replace: the tab shell, the Review card views, the hand-drawn Approve sheet. Khushal leaned this way in his Question Tree approval.

Decision (Khushal, 22 Nov): Reshape in place. Khushal challenged "solid and well tested". Corrected: the sending core (save first, one ID per operation, receipt check) is sound. The read side carries his problems, and the offline layer is over-built in places. It is a base to keep and repair, not proven on a device.

Affects every Ticket boundary, the order, and how much of today's 21,700 lines of app code each Ticket inherits.
1.1a If fresh: which current pieces carry over as they are (outbox, decision operations, markdown, voice, artifact viewer)?
1.1b If in place: which part goes first, so later parts build on it?
1.2 Which strip candidates stay?settled
Recommended answer · Group 1, sent 22 Nov

Strip: tab bar hosting, the custom back-swipe code, Chief swipe diagnostics, the "Try again" cover screen, status notes and "Sent" toasts, long-press menus and previews, Feedback (no server route, not on web), the Steer / Queue / Send now composer menu. Keep behind the Settings gear: Usage, Ideas, VPS, the standalone Goals list. Goals stay on Chief and Manager pages. Before the menus go, Remove blocker and Edit recap on Manager pages need visible buttons.

Decision (Khushal, 22 Nov): Strip as proposed, including the Steer / Queue / Send now menu. New rule: nothing is edited in the app; the composer is the only place to type. Edit recap, recap edits, renames and goal text edits go. Confirmed: no proposal text edits before approval (send back with a note instead). Remove blocker is removed.

Affects the shell Ticket and the scope of every page Ticket. Candidates: tab bar hosting, hidden navigation-bar delegate, Chief swipe diagnostics, network banners and "Sent" toasts, Feedback, Ideas, VPS, Usage, Goals screens.

2. Live data and freshness part 1

2.1 What single read model feeds the queue, the badge, the Sidebar and the pages?settled
Recommended answer · Group 1, sent 22 Nov

Keep the navigation-view stream as the one read model, and repair it. The main cause of staleness is the Review screen's own memory of shown cards, which only a restart clears. Pull never replaces a live stream. Repairs: fresh server data on every app open and on pull, a heartbeat check of about 30 seconds, connection state reset, fewer full reloads (no reload on brief inactive moments, read ahead a few cards only). This can ship first as a quick win.

Decision (Khushal, 22 Nov): Fix inside the current read model, as recommended.

Affects parts 1, 2, 3, 6 and 7. Today the navigation-view stream feeds all of them. The answer decides if the data Ticket is a repair or a replacement, and if the server must change.
2.1a When does the app become current: launch, return to foreground, pull to refresh, network change?
2.1b How many server reads may the phone make, so it never overloads the server again?
2.2 What does the app show from its saved copy before the server answers?settled
Recommended answer · Group 2

Every screen shows its saved copy at once and replaces it silently when the server answers. A card never acts on stale data: a decision on a proposal that changed is refused by the server and handled as in 3.2.

Decision (Khushal, 22 Nov): Accepted as recommended.

Affects parts 1, 2 and 6. "Feels instant" needs a saved copy at once. "Shows stuff from ages ago" says the current saved copy is wrong. One rule must serve every screen.
2.2a On the summary screen, can a count from the saved copy show before the server confirms it?

3. Sending and offline work part 5

3.1 Which actions take effect on screen at once and go through later, and which must wait for the server?settled
Recommended answer · Group 2

Take effect at once and go through later: approve, return, skip, reply, mark read, Chief and conversation messages, voice, photos. Mark read joins the outbox (it moves a read position, so it is safe to repeat). Ask answers: card leaves at once and the answer is queued, but the server needs an answer receipt so the phone can tell "my answer landed" from "too late" (a small server change, see 6.1). Rare Ticket actions (reviewer or ceiling only, backlog, recap request, blocker removal, worker setup) wait for the server inside their sheet, with no banner.

Decision (Khushal, 22 Nov): Accepted as recommended, including queued ask answers. A late ask answer becomes an ordinary message in that conversation. Known limit raised to Khushal: queued work sends only while the app is open.

Affects parts 2, 4, 5 and 6. Actions: approve, return, skip, reply, mark read, ask answers, permission answers, Ticket actions, attachments, voice.
3.2 When queued work cannot go through, how does the app tell Khushal without banners?settled
Recommended answer · Group 2

In place, on the item itself, like Messages: a refused decision brings its card back to the queue with the reason and the draft kept. A message that cannot go through stays in its conversation with a quiet retry mark. An ask that was answered elsewhere just leaves. No cover screen, no banners.

Decision (Khushal, 22 Nov): Accepted as recommended.

Affects parts 2, 5 and 6. Cases: a refusal, a reviewer change while the card is open, an ask that is already answered elsewhere, a send that stays uncertain.
3.3 Do all screens send through one shared path, built on today's outbox and decision operations?settled
Recommended answer · Group 2

Yes: the existing outbox, extended with mark read and ask answers. Simplify it where the server already protects us: messages can be replayed safely because the server de-duplicates them, which removes most "uncertain" states.

Decision (Khushal, 22 Nov): Accepted as recommended.

Affects who owns the sending code, and whether Review, Conversation and Ticket Tickets can run in parallel.

4. Review queue part 2

4.1 Who splits the queue into proposal, message and ask cards: the phone or the server?settled
Recommended answer · Group 3

The phone. The review window already carries proposals, messages and asks, and the badge counts all three. The phone builds single-purpose cards from those parts and reads an ask's wording from its conversation, as web does. No server change for the queue itself.

Decision (Khushal, 22 Nov): Accepted as recommended.

Affects parts 2 and 7. The web joins a Ticket's ask to that Ticket's card. The approved iPhone design gives each card one purpose. A server change moves work into a server Ticket.
4.2 After the summary screen, when does the app return to it?settled
Recommended answer · Group 3

The summary screen on every cold launch, and on return after a few minutes away. A short switch away resumes the open card. An unsent draft is never lost, and its card comes first when Khushal taps into the queue.

Decision (Khushal, 22 Nov): Not time-based. Follow navigation: an artifact or page opened from a card returns to the same card; going to Chief, a Manager or another Sidebar destination and back shows the summary; a fresh launch shows the summary. Leaving the app and coming back keeps Khushal exactly where he was. Only if that card was handled elsewhere meanwhile does he see the summary screen.

Affects parts 2 and 3. For example: every return from the background, or only after some time away, or never while a card is open with a draft.
4.3 Do Review and the Ticket page share one proposal decision control and its sheets?settled
Recommended answer · Group 3

Yes. Review and the Ticket page already share the Approve sheet, so one shared decision control and sheet, owned by the sheets work.

Decision (Khushal, 22 Nov): Accepted as recommended.

Affects parts 2, 4 and 6. If shared, one Ticket owns it and the other depends on it.
