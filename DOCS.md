# The Planner — what it is and how it works

This document is written as the system is built, stage by stage. It is for a smart reader who does not write code.

## What the planner is

The planner is a personal planning system that runs entirely on one computer. It replaces a folder of markdown files with a small database and a web page. It keeps track of four kinds of things:

- **Sprints** — two-week pushes with a written kickoff (why this sprint, what the bet is) and a written review at the end.
- **Sprint items** — the meaningful chunks of work a sprint is made of.
- **Tickets** — individual pieces of work small enough to hand to an AI agent.
- **Days** — one page per day: a morning brief, a plan for the day, and the day's ticket list.

There is also a simple list of **ideas** — things worth remembering that aren't work yet.

The human uses a web page. AI agents use a command-line tool. That split is deliberate: every decision that matters — approving work, granting permissions, closing things out — exists only in the web page, so an agent cannot take a decision that belongs to the human.

## The one rule everything follows

Agents never change the record directly. An agent that wants to move work forward files a **proposal**. A piece of code called the resolution engine is the only thing that can turn a proposal into a real value or move a ticket to its next stage. Some proposals are approved automatically (when the human has granted room in advance), and everything else waits for the human. And every change, by anyone, writes a line into an event log that is strictly append-only: the log itself is never edited or trimmed. The records the log describes do change — a ticket's fields update, and taking a ticket off a day's list removes that link — but each such change leaves its own permanent line in the log, so the history of what happened is never lost.

## How far an agent may go: the ceiling and the at-cap rule

Every ticket carries a permission with two parts:

- **The ceiling** — how far along its pipeline agents may push this ticket on their own.
- **At the cap** — what agents may do once the ticket reaches that ceiling: either **stop** (don't even suggest anything) or **propose** (draft the next step and park it for approval).

Below the ceiling, agent proposals are accepted automatically and the ticket advances. At the ceiling, the at-cap rule decides. And whenever the human approves a step, they must say in the same breath how far the agent may go next — the system refuses an approval that doesn't answer that question. New tickets start with the tightest sensible grant: the agent may draft a success condition, and nothing moves without approval.

## A ticket's life

A ticket moves through fixed stages: first it needs a **success condition** (what does done mean?), then an **approach** (how, roughly?), then a **plan** (concretely, step by step), then the work happens (**in progress**), then the result waits for checking (**needs review**), and finally it is **done**. A ticket can also be **dropped** at any point — only by the human. Each stage has exactly one blank to fill; filling it (and having that accepted) is what moves the ticket one stage forward. The human can always jump a ticket anywhere; agents never can.

## Status of the build

- **Stage 1 — contracts (done):** the skeleton exists: the database's table definitions, the exact vocabulary (every state, status, priority, and permission value), the shapes of every stored object, the configuration file with every tunable number, the interfaces where outside services plug in (agent spawning, the morning-brief writer, chat), and the full list of web addresses and command-line verbs the finished system will answer to. None of the behavior exists yet — this stage fixes the shapes so everything built later has to agree with everything else.
- **Stage 2 — the measuring stick (done):** one command, `./verify`, runs every check the specification demands — code style, type checking, the unit tests, a build check, and the browser tests — and prints a scoreboard of all 36 acceptance items ending `VERIFY: N/36 PASS`. It was built before the implementation on purpose: right now it honestly reports 0/36, and the rest of the build is the work of turning each line green. It also refuses to count tests that have been switched off or hollowed out — it scans for that and fails loudly.
- **Stage 3 — the rules (done):** all of the system's judgment now exists as tested code, before any server or screen. The resolution engine enforces everything described above: one pending proposal per blank (a newer one replaces the older, and the replacement is recorded); automatic acceptance strictly below the ceiling; the mandatory "how far next" answer on every human approval; the special ending where finished work goes to review unless the human had already granted straight-to-done. The day machinery knows what "today" means (the day flips at 5am, not midnight) and how the morning handover works: it closes yesterday with a count of what got done, carries forward what didn't, and asks the brief-writer for a plan — skipping that entirely if the human already planned the day. The dispatcher's bookkeeping is in place: an agent claims a ticket by winning a single atomic database update (two agents can race; exactly one wins), holds it on a 15-minute lease it must keep renewing, and loses it if it goes quiet or dies. Two failures in a row on the same ticket trip a breaker that parks it until the human clears it. And the importer reads the old markdown planning folder into the database — proven against a frozen copy of the real planning data, item for item, with an explicit list of everything it chose not to import (nothing is ever dropped silently), and safe to run twice (the second run imports nothing new). The scoreboard stands at 22 of 36.
- **Stage 4 — the server (done):** the rules now answer the door. One local process serves a JSON interface for every action in the system, and it enforces who may do what: requests from a working agent must carry a valid claim on the ticket they're touching (a stale or borrowed claim is refused, and the refusal names what was wrong without ever revealing the live claim itself); the actions reserved for the human — approving, granting, unblocking, dropping, freezing, deciding the day plan — refuse agents entirely. A live feed announces every change so screens can refresh themselves; the feed is only a doorbell, never the data. The dispatcher and the morning boundary job now actually run on their schedules (in testing they run only when explicitly ticked, so tests are exact). The command-line tool agents use is complete: every verb talks to the server, returns clean machine-readable output, and deliberately contains no approval powers at all. Four review findings worth naming, all caught by the independent reviewer and fixed: a path that leaked the live claim token into an error detail; a check that ran validation before verifying the claim; a number that could sneak into a date field untyped; and an environment value that could trick the tool into reading the wrong input.
- **Stage 5 — the screens (done):** six screens on one small design system whose entire personality lives in a single token file. Day: the morning brief, the proposed plan with accept/invalidate per line, the day's tickets, and the day's chat. Review: the one-at-a-time approval walk — and the approve button physically refuses to work until "how far may the agent go next" has been answered, both halves. Board: every ticket by stage. Ticket: the whole story of one piece of work — the four blanks, the permission dials, links, runs, history, chat, and a copy button that produces a plain-text block for pasting anywhere. Sprint: the kickoff (locked once frozen), the items with progress rollups, and the review. Backlog & Ideas: what's waiting, and what's merely interesting. The reviewer's best catch here was in the markdown renderer: a crafted link that browsers would quietly treat as runnable code; it's now impossible to express.
- **Stage 6 — the browser proof (done):** thirteen browser tests drive the real thing end to end — a real server, a real database file, real Chromium, and the real command-line tool running as a subprocess, with two independent browser windows open where the test demands proof that a change made in one place appears in the other without anyone refreshing. They cover: creating work from the command line and watching it appear on the Board; a proposal surviving the trip through the approval screen with the mandatory "how far next" answer; the morning boundary producing a brief and a plan; replanning; a full dispatcher round trip from claim to done; refreshing mid-flow and losing nothing; and the two migrations — the synthetic fixture and the frozen copy of the real planning data, imported twice to prove nothing duplicates. The full-suite run caught one genuine integration bug the individual tests had missed: the page was never loading the Sprint and Backlog screens' code at all — two script lines missing from the served page. Fixed; the scoreboard reached 36 of 36.
- **Stage 7 — dogfood (Level A done; Levels B and C recorded in DOGFOOD.md):** Level A is a scripted walkthrough of the whole workflow — a ticket taken from creation through every gate to done, with every approval carrying its grant, one approval edited, one proposal superseded, a recap written and overwritten, a blocking link proven to block dispatch and then cleared, a claim taken through the test dispatcher, and the final human approval — asserting the state after every step. It runs inside `./verify` as item 35. Levels B and C use the real local agent runtime and live outside the deterministic gate; their evidence — event-log rows, run records, log file paths — lives in DOGFOOD.md.

## How a day flows

At 5am the system closes yesterday: it counts what got done, notes what didn't, and carries the unfinished tickets forward as candidates. It then asks the brief-writer for a morning brief and a proposed plan for the new day. If you'd already planned the day yourself, it doesn't presume — the proposal step is skipped. You wake to a brief and a suggested plan; you accept it line by line, accept it all, or throw it out and plan by hand. Through the day, agents work whatever tickets their grants allow, filing proposals that either advance automatically or queue for your morning-coffee approval walk. Quick capture works through the day's chat: the system itself provides the chat panel and the command-line verbs for creating tickets and ideas, and the day-chat agent's written instructions (its skill document) tell it to file anything you toss in that sounds like work as a ticket or an idea right away, at the lowest priority, for later sorting. The filing is the agent doing its instructed job through the command-line tool — it is not something the server does on its own.

## What the command-line verbs do

The `plan` tool is for agents; every verb talks to the server and answers in machine-readable JSON. `ticket create/show/list/set` manage tickets (set covers only priority, deadline, day and sprint placement — permissions are never settable here). `propose <field>` files a proposal with the text piped in; `recap` writes the running summary; `note <field>` leaves guidance on a blank without touching it. `item`, `sprint show`, `idea`, `day`, and `link` do what they say. `run heartbeat/close` are how a dispatched agent keeps its claim alive and reports how its run ended. `queue approvals/pickup/overdue` are read-only views of what's waiting. There is deliberately no verb for accepting, approving, granting, or unblocking anything — those live only in the human's web interface. `plan serve` runs the server; `plan seed` imports the old markdown system or creates the demo dataset.

## What the skills are for

Four short documents under `skills/` teach specific agents their jobs: **planning-worker** — how a dispatched agent works a ticket through the CLI (orient, propose, recap, heartbeat, never ask questions); **planning-boundary** — the contract for writing the morning brief and plan proposal; **planner-main** — how the day-chat agent operates the queues through the CLI, including its standing instruction to file quick captures (work or ideas mentioned in chat) immediately as tickets or ideas via the CLI; **planning-executor** — how an agent executing an in-progress ticket works, including the review discipline at the checking stage: run the independent reviewer against the result and the review notes, fix what it finds, update the notes, and leave the final say to the human.

## The Sprint Overview page (redesign)

A sprint is now two pages, switched by a small pair of tabs at the top: **Sprint Overview** and **Sprint Tracking**. Tracking is the list of items and their tickets. Overview is where the thinking lives, in three headed sections you read top to bottom: **Kickoff** (why this sprint, the bet, what it rests on, and what could go wrong), **Mid-sprint Review** (where we stand, what's changed, what to adjust — written at the halfway point), and **Sprint Review** (how it went, at the end). Every section is just headed writing you edit in place — the same feel as the daily overview: click a line, type, click away, and it saves on its own. One section is open at a time depending on how far the sprint has gone: a brand-new sprint opens on Kickoff, a sprint with a mid-point note opens on the Mid-sprint Review, and a sprint being wrapped up opens on the Sprint Review.

Nothing on this page locks or commits — there are no buttons and no colour. This is a deliberate change from the earlier design, where the Kickoff and Review could be "frozen" shut. Freezing is gone from the sprint; the only place an edit is still made permanent by a button is a ticket's Approve. The old freeze machinery and the old weekly-addenda notes still exist underneath, switched off and out of the way, so the change can be undone if it's ever wanted.
